# Issue 与 PR 规范

Issue 用于记录可复现的问题、明确的需求和可验收的维护工作。一个 Issue 对应一个问题或交付目标；独立任务分别跟踪，相关记录互相链接。小型且明确的修正可以直接提交，无需补造 Issue。

## 创建 Issue

先搜索已有记录；重复问题补充到原 Issue。使用 `.github/ISSUE_TEMPLATE/` 中的表单，标题保留类型前缀，并写出具体对象与结果：

| 类型 | 标题示例 | 必要信息 |
| --- | --- | --- |
| Bug | `[Bug] 笔记页：切换文章后进度未重置` | 页面或命令、实际与预期、复现步骤、环境 |
| Feature | `[Feature] 笔记搜索：支持键盘选择结果` | 使用场景、预期效果、范围与非目标、验收条件 |
| Task | `[Task] 基础设施：补齐发布说明模板` | 目的、工作范围、验收条件、验证方式 |

页面问题提供含 Hash 的完整 URL；笔记问题提供文章路径或章节。构建问题提供命令、Node.js / pnpm 版本和相关日志。无法确定的信息标注“未知”，补充观察时间，不填猜测值。截图和日志作为证据，排除凭据及私人信息。

验收条件写成可观察的结果，例如“从搜索结果打开文章后，侧栏展开到该文章”，避免只有“优化体验”“完善基础设施”。

## 分诊与标签

维护者先确认是否重复、信息是否充分，再决定范围、优先级和负责人。信息不足时说明缺少什么；暂不实施时记录理由。优先级依据影响范围、是否阻断使用和是否存在替代办法，写入 Issue 正文即可。

Issue 与 PR 共用以下分类标签；维护者使用前在 GitHub 仓库中确认或创建。每条记录选择一个主要分类，`breaking-change` 可附加：

| 标签 | 用途 |
| --- | --- |
| `bug` | 行为错误、回归 |
| `enhancement` | 新功能、体验改进 |
| `documentation` | 笔记内容、文档、说明 |
| `maintenance` | 构建、CI、内部重构与仓库维护 |
| `dependencies` | 依赖升级 |
| `breaking-change` | 破坏既有使用方式的变更 |

表单本身不依赖预先存在的标签；标签由维护者分诊时补充。Release 分类读取 PR 标签，关联 Issue 的标签需要在 PR 上核对；未分类 PR 会进入“其他变更”。

## 实施与 PR

实施中将关键决策、范围调整和依赖补充到原记录；需要拆分时链接子任务。PR 使用 `.github/pull_request_template.md`，并满足：

- 标题遵循 [提交规范](conventional-commits.md)，正文解释触发问题、变更后的行为及必要的取舍。
- 写明实际执行的验证命令与结果；未执行的检查说明原因，不能勾选为通过。
- 界面变化提供必要的前后对照；架构、脚本、部署或主题约定变化同步维护 `AGENTS.md` 及对应设计文档。
- 完整解决问题时使用 `Fixes #编号` 或 `Closes #编号`；仅讨论、部分实现或仍待验证时使用 `Refs #编号`。没有关联记录时写“无”。
- 默认使用 Squash 合并，核对最终提交标题及正文；采用保留提交的方式合并时，每个工作提交都应符合规范。

## 关闭条件

完成类 Issue 按验收条件逐项核对，留下对应 PR / 提交及验证结果后关闭。涉及线上行为时还需确认目标版本部署成功；自动关闭后尚待线上验收的记录应继续跟踪，必要时重新打开。

重复、取消或不采纳的记录可以关闭，但要说明原因及后续去向。重新出现同一问题时，补充新证据并重开原记录，或链接新的回归 Issue。

表单语法依据 [GitHub Issue Forms 文档](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms)。
