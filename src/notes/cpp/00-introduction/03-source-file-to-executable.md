# 从源文件到可执行程序（From Source File to Executable Program）

在[编译并运行第一个 C++ 程序](02-choosing-cpp-development-tools.md#使用-gcc-编译)中，一条 `g++` 命令把 `main.cpp` 变成了可执行文件。实际项目中，还会遇到头文件、目标文件、库，以及构建配置和调试信息。它们并不都是源文件依次变换后产生的中间结果。

本篇沿用普通桌面终端程序，追踪源代码怎样经过转换与组合形成程序，再区分各类文件由谁读取、在什么时候需要，以及工具与环境怎样参与这个过程。

## 常见工具链的构建过程

把源代码及其依赖处理成目标产物的过程称为构建（build）。编译器驱动程序会协调其中的转换与组合工作；共同完成这些工作的一组工具称为工具链（toolchain）。

下面展示常见工具链中经过汇编代码的一条构建路径。图中先列职责，随后再把它们对应到实际文件：

```text
C++ 源文件
    │  预处理（preprocessing）
    ▼
预处理后的源代码
    │  狭义编译（compilation proper）
    ▼
汇编代码（assembly code）
    │  汇编（assembly）
    ▼
目标文件（object file）
    │  与其他目标文件及所需的库一起链接（linking）
    ▼
可执行文件
```

### 标准翻译与工具链实现不是同一层

C++ 标准描述源程序经过哪些翻译阶段（phases of translation），规定符合要求的程序应当呈现什么行为，并区分哪些违规需要诊断。它不要求编译器把每个阶段实现成独立进程，也不要求磁盘上实际出现固定名称的中间文件。

某个实现可以合并相邻阶段，也可以直接生成目标文件而不保存汇编文本。**这张图展示的是常见工具链中的一条构建路径，不是 C++ 标准强制规定的进程、文件数量或内部实现。**一次成功构建不一定会在目录里留下每一阶段的文件。

> [!IMPORTANT] 各阶段的职责
> 在这条构建路径中，**预处理处理指令并组织纳入的源代码内容；狭义编译分析语言含义并生成目标相关代码；汇编将汇编表示转换为目标代码及链接所需的信息；链接组合目标文件与所需的库，形成输出产物。**
>
> 这些职责用于判断当前得到什么结果、失败发生在哪一步。具体由几个工具执行、是否保存中间文件，则需要按实现核对。

## 源代码处理形成翻译单元

沿用输出问候文本的 `main.cpp`：

```cpp
#include <iostream>

int main() {
    std::cout << "Hello, C++!\n";
    return 0;
}
```

`main.cpp` 是直接交给驱动程序处理的源文件。头文件（header file）通常保存供源文件使用的声明、类型等源代码信息；声明（declaration）在这里让编译器知道名称及其使用方式。头文件也可以提供实现，因此不能把它理解成只含名称的清单。

预处理会处理 `#include <iostream>`，按照实现的查找规则取得 `<iostream>` 的相应内容，使这些内容参与 `main.cpp` 的处理。它还会处理其他预处理指令，例如按条件保留源文本。标准库头 `<iostream>` 的名称没有 `.h`，不必把它改写成 `iostream.h`。

| 文件角色 | 常见名称 | 在这里怎样参与构建 |
| --- | --- | --- |
| 源文件 | `main.cpp`；也常见 `.cc`、`.cxx` | 作为一次翻译的起点交给驱动程序 |
| 头文件 | `greeting.h`、`greeting.hpp`；标准库头如 `<iostream>` | 由包含它的源文件纳入处理，可以同时被多个源文件使用 |

对于本篇这种使用 `#include` 的组织方式，一份源文件及其纳入内容经过预处理和后续转换，形成词法记号（token），也就是分析程序结构与含义时使用的基本单位。这些记号共同构成一个翻译单元（translation unit），作为整体接受语法、语义分析和翻译。

预处理后的源代码可以保存为文本文件，常见后缀有 `.ii`、`.i`，具体约定取决于工具与选项。本篇的 GCC 命令使用 `main.ii` 保存预处理后的 C++ 文本。看到这些后缀时，要核对产生和读取它们的工具，不能把它们当成两个连续的必经阶段。

> [!IMPORTANT] 翻译单元是语言分析的单位
> **源文件与头文件描述源代码的组织；翻译单元描述哪些内容一起接受语言分析。**翻译单元不要求对应磁盘上一份固定后缀的文件，实现可以在内部直接传递处理结果。
>
> 判断哪些代码会一起接受语法、语义检查时，应追踪源文件及其纳入内容，而不是仅按目录中的文件数量判断。

## 编译与汇编产生目标文件

狭义编译接收预处理后的源代码，对相应翻译单元进行语法和语义分析，检查它是否符合 C++ 规则，并生成面向目标平台（target platform）的代码。目标平台是程序准备运行的处理器与系统环境。

编译器可以先产生汇编代码。汇编代码是目标处理器机器指令的一种文本表示，在本篇的 GCC 命令中保存为 `main.s`。汇编器（assembler）再将其转换为机器代码，并生成后续组合所需的信息；集成在编译器中的汇编器也可以完成这项工作。

这条路径得到的目标文件（object file）保存当前翻译的结果，包括目标代码、数据以及链接所需的信息。常见后缀有 `.o`、`.obj`，具体命名由工具及其选项决定。

例如，`main.o` 包含 `main` 的实现，但输出设施的一部分实现仍来自其他编译产物。目标文件和可执行文件虽然都可能包含机器代码，在构建中的职责却不同；将 `main.o` 简单改名为 `hello` 不会替它完成链接。

> [!IMPORTANT] 目标文件与可执行文件的区别
> **目标文件保存当前翻译的结果，通常还需要参与链接；可执行文件是已经按程序加载要求组织的产物。**因此，已经生成目标文件，只能说明构建走到了相应位置，不能据此认定已经生成完整程序。

## 库与链接补齐程序所需的实现

库（library）把供其他程序复用的代码及其使用接口组织起来。一个库可以直接提供源代码，也可以提供预先编译的产物。采用头文件组织接口时，库可能只需提供头文件，也可能同时提供头文件和编译产物。

对问候程序，`#include <iostream>` 使编译器得到使用 `std::cout` 所需的信息；输出设施的一部分实现则由标准库已有的编译产物提供。**包含头文件与加入库的编译产物，是构建中不同的工作。**实现已经在头文件中提供的部分会随当前翻译单元处理，需要其他编译产物提供的部分则要在后续组合中得到支持。

### 符号记录各产物提供什么、需要什么

目标文件需要让后续工具知道自己提供什么、还需要找到什么。工具链使用符号（symbol）识别需要跨编译产物匹配的函数或数据等程序实体（entity）。实际提供某个实体、能够满足相应引用的程序内容，是这里所说的定义（definition）。

`main.o` 需要一部分输出实现，却没有包含相应定义，这项需求构成外部引用（external reference）：

```text
main.o：提供 main 的实现，需要输出设施的部分实现
标准库的编译产物：提供相应的输出实现
```

链接器（linker）读取目标文件与参与链接的库，根据符号处理这些引用，并构造当前需要的输出产物。构建普通程序时，这个产物通常是可执行文件：

```text
main.o         ─┐
所需的编译产物 ─┴─> 链接器 ─> 可执行文件
```

上面的“输出实现”用于说明职责，并不是实际符号的拼写。符号也不是源代码名称的简单文本副本；工具链按照目标平台的规则表示这些信息。

前面使用的 `g++` 构建命令会安排链接，并自动加入 C++ 标准库。驱动还可能加入运行支持（runtime support）所需的其他产物，例如负责准备启动条件并将执行引向 `main` 的支持代码。因此，命令中只写了一个 `main.cpp`，不代表这个源文件包含了程序所需的全部实现。

> [!IMPORTANT] 链接处理需求与定义的对应关系
> **目标文件可以同时提供定义和保留对其他实现的引用；链接根据符号处理这些引用与相应定义的关系，组织输出产物。**当前翻译单元能够生成目标文件，不表示链接所需的实现已经齐备。
>
> 这项关系用于解释为什么源代码已经通过编译，构建仍可能因缺少库或所需定义而在链接阶段失败。

### 静态库与动态库怎样提供实现

预先编译的库有不同组织方式，这会影响链接时读取什么，以及运行时还需要什么：

| 库的形式 | 常见文件示例 | 对构建和运行的影响 |
| --- | --- | --- |
| 静态库（static library） | `libgreeting.a`、作为静态库提供的 `greeting.lib` | 通常归档一组目标文件，链接时从中取得所需成员，把相应代码和数据并入输出产物；运行时不需要再读取原静态库文件来获得这部分实现 |
| 动态库（dynamic library），也常称共享库（shared library） | Linux 的 `libgreeting.so`、macOS 的 `libgreeting.dylib`、Windows 的 `greeting.dll` | 实现保留在独立库中，由系统的加载机制在程序启动或运行时加载，程序再使用其中的实现 |

> [!IMPORTANT] 静态链接与动态链接怎样提供实现
> **静态链接把从库中取得的相应实现并入输出产物；动态链接让相应实现保留在独立动态库中，程序启动或运行时仍需加载它。**这个区别用于判断某部分实现是否已经随输出产物保存，以及运行时还需要提供什么。
>
> 对于链接时确定的动态库依赖，链接器会在程序中记录相应依赖信息，而不把该库的全部实现并入可执行文件。具体链接输入按平台与工具链核对。

同一个程序可以同时使用静态库和动态库。某个库采用静态链接，只说明这部分实现已进入输出产物，不能据此推断整个程序都没有动态依赖。标准库设施的实现也可能分布在头文件、静态库和动态库中；“C++ 标准库”并不等于一个固定名称或后缀的文件。

### 链接输入与运行时依赖需要分别辨认

对于通过头文件提供接口的预编译库，可以按职责追踪各阶段需要什么：

```text
编译：源文件 + 库的头文件             ─> 目标文件
链接：目标文件 + 库的链接输入         ─> 可执行文件
加载：可执行文件 + 所需动态库         ─> 准备执行
```

动态库的链接输入可能是动态库本身，也可能是配套的链接辅助文件。导入库（import library）就是后一种形式：它帮助链接器识别由动态库提供的实现，实际运行时仍需相应动态库。

例如，MSVC 的 `.lib` 既可能是静态库，也可能是配合 `.dll` 使用的导入库，需要结合库的说明辨认。这个例子说明后缀与文件职责并非一一对应；其他工具链的具体输入同样应按其规则确认。

**获得头文件、让链接器识别所需实现、让运行环境能够加载实际依赖，是三项不同条件。**使用预编译库时，要分别确认这些条件已经满足。

## 分别编译让翻译单元独立产生目标文件

同样的组合关系也适用于自己编写的多个源文件。保持输出问候的目标不变，将用户代码分工为：`main.cpp` 保留入口并使用问候功能，`greeting.cpp` 提供它的实现。

每个源文件及其纳入内容各自形成翻译单元，分别完成翻译，再在链接阶段组合。这种组织方式称为分别编译（separate compilation）：

```text
main.cpp      ─> 翻译单元 ─> main.o      ─┐
greeting.cpp  ─> 翻译单元 ─> greeting.o  ─┼─> 链接器 ─> 程序
所需的库     ───────────────────────────┘
```

图中的两个翻译单元分别包括各自源文件所纳入的内容。这里，`main.o` 记录对问候功能的引用，`greeting.o` 提供相应定义，输出设施仍由标准库的相关产物支持。链接器组合这些产物，不会把它们重新当作 C++ 源文本解释。

若两个源文件都包含 `greeting.h`，这份头文件的内容会分别参与两个翻译单元的处理；它不会因被包含，就在这条普通构建路径中独立生成一个 `greeting.o`。

修改一个 `.cpp` 后，通常只需重新生成受影响的目标文件并再次链接；修改共同包含的头文件，则可能使多个翻译单元需要重新处理。分别编译让构建能够复用未受影响的结果，但哪些结果已失效，还需要根据依赖关系判断。

组合的产物必须具有相互兼容的文件格式、目标平台和工具链约定。`.o` 与 `.obj` 都可以承担目标文件的角色，这并不保证任意两个这样的文件都能互相替换。

## 生成可执行文件之后还需要加载

链接得到可执行文件之后，启动程序还需要系统的加载器（loader）将程序及其依赖装入内存，准备执行条件。对于链接时记录的动态库依赖，加载机制需要找到兼容的实际库文件；缺少文件或版本不兼容时，程序可能在进入 `main` 前就启动失败。`.so`、`.dylib`、`.dll` 都可能承担这种运行依赖的角色，具体查找规则由目标系统与工具链决定。

> [!IMPORTANT] 生成可执行文件与成功启动是不同条件
> **生成可执行文件不保证程序能够成功启动。**对于存在动态依赖的程序，运行环境还必须能够找到并加载兼容的库。这一区别用于判断为什么编译、链接都已成功，程序仍可能在开始执行用户代码前失败。

构建时使用的头文件目录、链接时搜索库的目录，以及运行时查找动态库的规则，需要分别核对。链接器曾经找到某个库，不保证把可执行文件移到其他目录或机器后，系统仍能找到对应的动态库及其所需版本。

## 观察 GCC 的停止位置

回到第一个程序中尚未拆分的 `main.cpp`，GCC 驱动程序允许构建停在典型流程的不同位置：

下表用于观察和查阅。需要理解每条命令的输入、停止位置与输出之间的对应关系，具体选项和文件名不要求逐项背诵。

| 命令 | 停止位置 | 本例指定的输出 |
| --- | --- | --- |
| `g++ -std=c++23 -E main.cpp -o main.ii` | 预处理完成后 | `main.ii`：预处理后的源代码文本 |
| `g++ -std=c++23 -S main.cpp -o main.s` | 编译完成、汇编之前 | `main.s`：汇编文本 |
| `g++ -std=c++23 -c main.cpp -o main.o` | 目标文件生成、链接之前 | `main.o`：目标文件 |
| `g++ main.o -o hello` | 链接完成后 | `hello`：可执行文件，Windows 目标上通常为 `hello.exe` |

前三条命令各自从同一个 `main.cpp` 开始，只改变停止位置。最后一条以第三条成功生成的 `main.o` 为输入，完成链接。

`-E`、`-S`、`-c` 选择停止位置，`-o` 指定输出名称。中间文件可以为了观察过程显式保存，也可以由驱动在一次完整构建中临时生成或在内部传递。可执行文件也不一定有固定扩展名：Linux、macOS 中常直接使用 `hello` 这样的名称。

## 工具与环境决定怎样执行这些步骤

源文件、头文件与库是工具读取的输入，构建环境（build environment）则包括所选工具、配套开发资源，以及决定查找位置和目标平台的配置。环境设置会改变命令能否执行、读取哪份文件和生成哪种目标产物。

### IDE 与构建工具怎样调用工具链

编辑器与 IDE 可以提供编辑、构建和运行入口。Make、Ninja、MSBuild 这样的构建工具依据规则与依赖关系，安排需要执行的命令。CMake 通常根据项目描述生成供这些工具使用的构建文件，也可以调用相应构建工具发起构建。

例如，在一种使用 CMake 与 Ninja 的配置中，职责可以这样对应：

```text
CMake 读取项目描述 ─> 生成 Ninja 构建规则
Ninja 读取构建规则 ─> 调用编译器驱动及其他工具
编译器、汇编器、链接器 ─> 处理输入并生成产物
```

直接在终端运行 `g++ main.cpp -o hello` 时，可以不经过这层项目构建规则。IDE 中的“构建”按钮可能替我们完成这些调用；实际执行了什么，要查看项目配置和构建日志。

### 查找工具、头文件与库是不同的配置

| 需要找到什么 | 谁需要它 | 常见设置示例 |
| --- | --- | --- |
| `g++`、`clang++`、`cl` 等可执行工具 | 当前终端或发起构建的工具 | 工具的完整路径，或终端用于查找命令的 `PATH` 环境变量 |
| 头文件 | 预处理与编译过程 | 工具的默认头文件路径，以及构建配置中显式添加的头文件搜索目录 |
| 参与链接的库 | 链接器 | 指定库文件或库名称，以及库搜索目录；只添加目录不能代替选择实际库输入 |
| 程序依赖的动态库 | 系统的加载机制 | 目标系统规定的动态库查找与部署规则，不能直接用编译器的库搜索选项代替 |

这些查找行为受工具默认配置、命令选项、项目设置及环境变量共同影响。环境变量（environment variable）是终端及其启动的工具可以读取的命名配置值，`PATH` 就是例子。能够在终端显示编译器版本，只验证了这个驱动能够被找到和运行，还不能证明头文件、链接库与目标平台资源已经齐备。

软件开发工具包（Software Development Kit，SDK）提供面向某个目标平台的头文件、库及配套工具等资源。目标平台可能与运行编译器的机器不同；选择编译器、SDK 和库时，还需要核对它们是否支持同一个目标，以及彼此是否兼容。

工具名称与目标系统也不是一一对应的。例如，Clang 可以配合不同平台的链接器与库工作。判断文件格式、搜索规则与可运行条件时，应核对实际选择的目标和配套工具，而不能只看编译器名称。

## 辨认项目中的配置与辅助文件

项目目录中还会出现描述构建方式、记录依赖、保存调试信息或复用处理结果的文件。它们与程序代码有关，但各自服务于不同工具，不应全部串进“源文件逐步变成可执行文件”的直线流程。

下表供辨认文件职责时查阅，不要求背诵每一种后缀。当前需要能够判断的是一份文件服务于哪类工作，以及应由哪个工具读取。

| 类别 | 文件或目录示例 | 角色与主要读取者 |
| --- | --- | --- |
| 项目描述 | `CMakeLists.txt`、`.cmake`、`.vcxproj` | 对应的项目或构建工具读取，描述源文件、依赖及构建设置；具体语法由工具决定 |
| 构建规则 | `Makefile`、`build.ninja` | Make、Ninja 读取，安排命令及其依赖；可以由作者维护，也可以由其他工具生成 |
| 配置记录 | `CMakeCache.txt` | CMake 在配置过程中生成并再次读取的持久配置记录，例如所选工具和构建选项 |
| 依赖记录 | `.d` | 编译工具生成，供构建工具判断源文件及其包含内容的变化影响哪些产物 |
| 调试信息 | `.dwo`、`.pdb`；`.dSYM` 目录包 | 保存调试器需要的信息，由编译、链接或专门的调试信息处理工具生成；它们不承担可执行程序的角色 |
| 预编译头 | `.gch`、`.pch` | 预编译头（precompiled header）的常见产物，供编译器复用已处理的头文件内容；它们仍需符合当前编译条件，不替代最终目标文件与链接 |

调试信息也可以保存在目标文件或可执行文件内部，不一定形成独立文件。表中的后缀是不同实现的例子，辨认时先看信息的用途，再核对所用工具怎样保存和读取它。

这里的分类用于识别职责，不要求每个项目都生成表中全部文件。`build/`、`Debug/`、`Release/` 等目录也只是组织构建结果的方式；目录里的文件仍需按实际角色辨认，配置名称本身不能说明全部编译选项。

面对陌生文件，先确认是谁生成、谁读取，以及它保存的是源代码、编译结果、构建规则还是辅助信息，再按该工具的输入输出说明核对。是否参与链接、是否在运行时需要，应由这项职责判断，不能仅凭它与可执行文件放在同一目录判断。

## 按失败位置判断需要检查的条件

这些区分可以落回同一个问候程序及上面的库依赖关系：

| 失败位置 | 典型现象与对应判断 |
| --- | --- |
| 调用工具 | 终端找不到所选编译器驱动：构建命令尚未正常执行，先核对工具安装、路径与当前终端配置 |
| 预处理 | 报告找不到所包含的头文件：核对文件是否提供，以及头文件查找路径；补上库文件不能替代这项输入 |
| 狭义编译 | 删去所需包含后，`std::cout` 的名称信息不可用：当前翻译单元无法按规则分析这段用法 |
| 链接 | 参与链接的库未找到，或所需外部引用未能得到满足：核对实际库输入、搜索目录与产物兼容条件；相互冲突的定义也可能使链接失败 |
| 加载 | 可执行文件已经生成，却因缺少所需动态库等依赖而无法启动：核对运行环境及动态库的查找、版本与兼容条件 |

这些现象用于定位职责，具体原因仍以工具诊断和实际输入为依据。日常交流常把整个构建过程统称为“编译”；排查问题时，需要进一步确认失败发生在调用工具、语言处理、链接还是加载阶段。

前述核心关系用于辨认处理单位、构建产物及编译、链接、加载之间的边界。定位问题时，先依据这些关系确认当前处于哪一步，再检查这一步实际读取的输入与期望产物。

文件后缀、命令选项和具体搜索规则按需查阅。观察中间产物、接入库或更换工具时，按已确定的阶段核对对应工具的输入、输出与配置说明。
