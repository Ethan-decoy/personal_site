# 源代码中的空白与注释（Whitespace and Comments）

C++ 源文件本质上是一系列字符。翻译源代码时，编译器会把这些字符识别为具有独立语法意义的 token（词法记号）。例如：

```cpp
double front_left_pressure{2.0};
```

其中，`double` 是关键字，`front_left_pressure` 是标识符，`2.0` 是浮点数字面量，花括号与分号则分别承担相应的语法作用。空白与注释通常不描述程序需要完成的计算，却决定了源代码怎样分隔、组织和解释这些 token。

## 空白字符（Whitespace Characters）

源代码中最常见的空白字符（whitespace characters）是空格、制表符和换行符。在多数声明和表达式中，只要 token 的边界没有改变，一个空格、多个空格或一次换行通常具有相同的分隔作用：

```cpp
double front_left_pressure{2.0};
```

下面的写法虽然排版怪异，但表达的是同一条声明：

```cpp
double
front_left_pressure
{
    2.0
}
;
```

因此，C++ 通常不依靠缩进或换行表示代码的语法层级。缩进仍然十分重要，因为它把代码结构直接呈现给读者；现代格式化工具也正是通过统一空格、换行和缩进来减少无意义的排版差异。

### 空白并非处处都能省略

当相邻字符可能被识别为同一个 token 时，空白负责明确它们的边界：

```cpp
double front_left_pressure{2.0};
doublefront_left_pressure{2.0};
```

第一行以关键字 `double` 声明变量；第二行开头的 `doublefront_left_pressure` 会被识别为一个完整的标识符，已经不再具有相同含义。类似地，`+ +` 是两个运算符，而 `++` 是一个自增运算符。

空白也不是在所有位置都可以任意加入或删除。字符与字符串字面量中的空格可能属于数据本身，预处理指令通常由换行结束。更准确的理解不是“编译器会忽略所有空白”，而是：空白通常用于分隔 token，并在少数语言结构中具有额外作用。

## 注释（Comments）

注释用于在源代码中记录提供给读者的信息。C++ 在翻译过程中把注释当作空白处理，因此注释本身不会形成需要在运行时执行的操作。语言提供了两种注释形式。

### 行注释（Line Comment）

行注释从 `//` 开始，一直延续到当前行结束：

```cpp
// 调整气门前记录的气压
double pressure_before_adjustment{2.0};

double pressure_after_adjustment{1.8};  // 调整完成后的气压
```

`//` 既可以独占一行，也可以放在代码之后。换行结束当前注释，下一行重新按照普通 C++ 源代码处理。

### 块注释（Block Comment）

块注释以 `/*` 开始，以随后遇到的第一个 `*/` 结束，因此可以跨越多行：

```cpp
/*
传感器切换曝光后需要等待一段时间，
否则第一次测量可能仍处于过渡状态。
*/
int settling_time_ms{250};
```

块注释不能嵌套。在一个块注释内部再次写入 `/*`，不会开始一个新的内层注释；随后遇到的第一个 `*/` 仍会结束整个注释，其余字符将重新被当作源代码处理。

两种形式在语言规则中都有效。现代 C++ 项目通常使用 `//` 编写普通注释，需要多行时就在每行开头重复 `//`；这种写法便于单独修改每一行，也不会受到块注释无法嵌套的限制。`/* ... */` 仍然可以在项目规范或特定工具需要时使用。

翻译源代码时，每段注释会被替换为一个空格，行注释末尾的换行仍然保留。因此，下面的代码在语言层面可以被识别为 `int retry_count{3};`：

```cpp
int/* number of retries */retry_count{3};
```

这种写法把注释塞进了声明的结构，阅读时反而需要重新拼接代码，不应作为日常排版方式。注释能够出现在 token 之间，不代表每个合法位置都适合放置注释。

## 普通注释与文档注释（Documentation Comments）

C++ 标准只规定 `//` 与 `/* ... */` 两种注释语法。在这两种语法之上，文档工具和语言服务还会把带有额外标记的注释识别为文档注释（documentation comment），并将它与附近的声明关联起来。

常见形式可以整理为：

| 用途 | 写法 | C++ 语言中的本质 | 常见工具行为 |
|---|---|---|---|
| 普通行注释 | `// ...` | 行注释 | 只作为源代码说明 |
| 普通块注释 | `/* ... */` | 块注释 | 只作为源代码说明 |
| 行式文档注释 | `/// ...` | 内容以 `/` 开头的行注释 | 关联并说明紧随其后的声明 |
| 块式文档注释 | `/** ... */` | 内容以 `*` 开头的块注释 | 关联并说明紧随其后的声明 |

例如：

```cpp
// 传感器改变曝光后需要 250 ms 才能进入稳定状态。
int settling_time_ms{250};

/// @brief 设备允许连续执行的最大校准次数。
int calibration_limit{3};
```

第一段是留给代码读者的普通实现说明。第二段不仅可以被人直接阅读，还可以被 Doxygen、Clang 和 clangd 识别为 `calibration_limit` 的文档；编辑器因而能够在代码补全或悬停信息（hover）中显示它。

Doxygen 还支持 `//! ...`、`/*! ... */`，以及放在成员之后的 `///< ...`、`//!< ...`、`/**< ... */` 和 `/*!< ... */`。这些都是工具建立的约定，并没有为 C++ 增加新的注释语法。一个项目应当选定一致的文档风格，而不是混用所有受支持的形式。当前笔记采用现代 C++ 项目中简洁而常见的组合：普通注释使用 `//`，紧随声明之前的文档注释使用 `///`。

### 文档注释中的结构化命令

`@brief` 不是另一种注释写法，而是写在文档注释内部的 Doxygen 命令。文档注释负责把文字与声明关联起来，`@brief` 则明确指出随后的段落是这项声明的简要说明（brief description）：

```cpp
/// @brief 设备允许连续执行的最大校准次数。
///
/// 上限来自设备固件的校准保护机制。
int calibration_limit{3};
```

同样的结构也可以写在块式文档注释中：

```cpp
/**
 * @brief 设备允许连续执行的最大校准次数。
 *
 * 上限来自设备固件的校准保护机制。
 */
int calibration_limit{3};
```

`@brief` 的内容持续到空行或下一个分节命令为止；空行之后的段落作为详细说明。Doxygen 命令既可以使用 `@`，也可以使用反斜线，因此 `@brief` 与 `\brief` 含义相同。

在默认工具配置下，`@brief` 应当放进 `///`、`/** ... */` 等文档注释，而不是普通的 `//` 注释：

```cpp
// @brief 普通注释，工具不一定把它关联为接口文档。
/// @brief 文档注释，可以关联到紧随其后的声明。
int calibration_limit{3};
```

显式写出 `@brief` 并非始终必要。Doxygen 可以把单行 `///` 文档直接作为简要说明，一些项目也会配置为自动提取第一句话。LLVM 的编码规范因此更倾向直接写一句清楚的 `///`，避免为简单说明机械添加 `@brief`。若项目需要不依赖自动摘要规则的显式结构，使用 `/// @brief ...` 同样合理；关键仍然是遵循项目统一约定。

随着函数、模板和公共接口的引入，还会遇到 `@param`、`@return`、`@tparam`、`@note` 和 `@warning` 等命令。它们负责描述文档的内部结构，并不会参与 C++ 程序的运行；相应内容将在相关语言概念出现后再展开。

clangd 默认能够显示符号文档。若项目希望它进一步按照 Doxygen 规则解析文档中的命令，可以在 `.clangd` 中配置：

```yaml
Documentation:
  CommentFormat: Doxygen
```

这项配置只改变编辑器如何解释和呈现注释，不会改变 C++ 程序的语义。

### 可检索的任务标记

`TODO` 和 `FIXME` 等大写标签也经常出现在注释开头。许多编辑器扩展、静态检查器和项目脚本能够高亮或汇总这些标签，但 C++ 标准没有规定它们的含义。

`TODO` 表示仍需完成的明确工作时，不应只留下无法追踪的提醒。更可靠的写法会同时记录关联的问题编号以及删除临时代码的条件：

```cpp
// TODO(issue-184): 旧版传感器固件停用后删除此兼容路径。
```

`FIXME`、`NOTE` 和 `HACK` 的含义在不同工具与团队之间并不统一，使用前应遵循项目自己的约定。它们带来的价值在于可检索和可追踪，而不在于标签本身看起来醒目。

## 注释应当补充代码没有直接表达的信息

清晰的名称和代码结构首先负责说明程序正在做什么。下面的注释只是逐字复述初始化语句，没有提供新的信息：

```cpp
int retry_count{0};  // 将 retry_count 初始化为 0
```

如果读者仅凭变量名无法理解数据含义，应优先改善名称。注释更适合说明无法从代码本身直接看出的设计意图、外部约束或反直觉原因：

```cpp
// 传感器改变曝光后需要 250 ms 才能进入稳定状态。
int settling_time_ms{250};
```

这里的声明已经清楚表达对象保存的是稳定等待时间，注释进一步解释了为什么需要等待，以及数值 `250` 来自什么约束。

代码发生变化时，相关注释也必须同步更新。过时的注释会让读者在代码与文字之间作出错误判断，往往比没有注释更危险。简洁、准确并且仍与实现一致的注释，才是源代码中可靠的一部分。

相关语言规则可参阅 [C++ 工作草案中的词法约定](https://eel.is/c%2B%2Bdraft/lex)与[注释](https://eel.is/c%2B%2Bdraft/lex.comment)。工具约定可参阅 [Doxygen 的文档注释形式](https://www.doxygen.nl/manual/docblocks.html)、[`@brief` 命令](https://www.doxygen.nl/manual/commands.html#cmdbrief)、[clangd 的文档解析](https://clangd.llvm.org/features#documentation-parsing)与 [`Documentation.CommentFormat` 配置](https://clangd.llvm.org/config#commentformat)。关于注释风格与 `///` 的使用，可参阅 [LLVM Coding Standards](https://llvm.org/docs/CodingStandards.html#comment-formatting)；关于可追踪的 `TODO`，可参阅 [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html#TODO_Comments)。
