# 调用栈与栈帧（Call Stack and Stack Frames）

运费函数返回后，应付金额计算还要用原先保存的商品金额继续相加。实现需要让外层仍会用到的值保持正确，并使执行回到相应的调用位置。

调用栈（call stack）按嵌套次序组织尚未完成的调用；栈帧（stack frame）是常见实现中与一次活动调用有关的栈上数据区域。调用状态可以由寄存器、栈空间等共同承载，C++ 语言规定的是这些调用应有的行为。

## 嵌套调用呈现后进先出关系

沿用[嵌套调用中的运费计算](../05-nested-calls-and-independent-call-state.md#调用可以发生在另一次调用中)。下面是完整程序，金额仍按整数元记录，使用非负的小整数：

```cpp
#include <iostream>

int calculate_shipping_fee(int fee, int surcharge) {
    fee += surcharge;
    return fee;
}

int calculate_payable_total(int goods_total, int base_fee, int surcharge) {
    int total{goods_total};
    int shipping_fee{calculate_shipping_fee(base_fee, surcharge)};

    total += shipping_fee;
    return total;
}

int main() {
    int payable_total{calculate_payable_total(100, 5, 10)};
    std::cout << payable_total << '\n'; // 115
    return 0;
}
```

`main` 等待应付金额，应付金额函数又等待运费。运费函数正常返回后，应付金额函数才能完成运费的初始化与相加，再把最终结果交给 `main`。

栈（stack）是一种只从一端加入和移除元素的组织方式，这一端称为栈顶，另一端称为栈底。加入栈顶称为入栈（push），移除栈顶元素称为出栈（pop）：最后加入的元素先移除，即后进先出（last in, first out，LIFO）。

在用调用栈承载嵌套调用的常见模型中，进入内层调用相当于在栈顶增加一份调用记录；内层正常返回后，这份记录退去，外层记录重新位于栈顶。运费函数正在计算时，可以把当前关系画成：

```text
栈顶：最后进入的调用
┌──────────────────────────────────────────┐
│ calculate_shipping_fee   正在计算运费    │
├──────────────────────────────────────────┤
│ calculate_payable_total  等待运费结果    │
├──────────────────────────────────────────┤
│ main                     等待应付金额    │
├──────────────────────────────────────────┤
│ 更早的调用与实现状态（省略）             │
└──────────────────────────────────────────┘
栈底一侧：更早进入的调用
```

运费函数返回 `15` 后，应付金额函数继续把 `100` 与 `15` 相加，返回 `115`，最后 `main` 输出这个结果。图中的上下方向只表示调用的新旧次序；实际维护栈位置的指令与内存布局由实现决定。

> [!IMPORTANT] 调用栈与栈帧的关系
> **在用栈承载普通嵌套调用的常见模型中，调用栈按后进先出组织活动调用，栈帧承载与某次活动调用有关的部分状态。**内层正常返回后，外层继续尚未完成的工作。这个模型描述组织关系，具体栈帧的大小、内容与布局仍由实现决定。

## 栈帧承载一次活动调用的实现状态

一次活动调用所需的信息也常用活动记录（activation record）来描述。以栈空间组织的调用记录通常称为栈帧；它可以包含局部数据、保存的寄存器状态、返回位置及求值所需的空间，具体分配方式取决于实现。

处理器直接用于保存运算中数据的位置称为寄存器（register）。内层调用也可能使用寄存器，因此调用双方需要按约定维护外层后续仍需的值。有些值可以放在调用前后按约定保持其内容的寄存器中；有些值需要先保存到栈空间，返回后再取得；实现也可能重新计算某个值。

观察开篇程序中内层即将返回 `15` 的时刻，可以把语义上的需求与常见的机器承载方式对应起来：

| 调用需要维持的关系 | 解决的问题 | 可能的承载方式 |
| --- | --- | --- |
| 外层的 `total` 仍为 `100` | 内层返回后，还要把运费加到它上面 | 值保留在适当的寄存器或栈位置，也可能由实现重新取得或计算 |
| 内层把自己的 `fee` 从 `5` 改为 `15` | 按本次输入得到运费 | 参数值通过约定的寄存器或栈位置传入，再用于运算 |
| 内层把结果 `15` 交给外层 | 完成外层 `shipping_fee` 的初始化 | 结果通过约定的位置交回，例如结果寄存器 |
| 执行回到外层的调用位置 | 继续完成初始化，再执行相加 | 返回所需的信息帮助机器代码从相应位置继续 |

这里的“返回位置”帮助执行继续当前调用处的工作，不是让外层函数从头再执行一次。表中的值也不是固定的栈帧字段：外层的 `shipping_fee` 此时尚未完成初始化，不能把它画成已经保存 `15` 的对象；参数和结果也不一定需要各占一个栈槽。

栈帧的具体内容由编译器、目标平台的应用二进制接口（Application Binary Interface，ABI）和优化共同决定。ABI 让分别编译的调用双方对参数、返回值和保留状态采用兼容的约定；它还约束哪些边界，见附章[应用二进制接口：编译产物之间的契约](02-application-binary-interface.md#abi-固定分别编译边界)。栈帧是实现维护的调用数据，不是源程序中显式定义的某个 C++ 对象。

## 自动存储期不等于物理栈

存储期（storage duration）约束承载对象的存储至少需要维持多久；生命周期（lifetime）描述某个对象何时开始和结束存在。本节普通块作用域局部对象具有自动存储期（automatic storage duration），它们按代码块中的声明与控制流规则建立和结束生命周期。

对于这里的 `int` 局部对象，存储可用并完成初始化后，生命周期才开始；正常离开所属代码块时，生命周期结束。寄存器、栈槽及其他机器安排，则是实现承载这些语义的方式。

保留开篇的运费函数和 `main`，只用下面的定义替换 `calculate_payable_total`。输出仍为 `115`，但 `shipping_fee` 位于一个单独的内部代码块中：

```cpp
int calculate_payable_total(int goods_total, int base_fee, int surcharge) {
    int total{goods_total};

    {
        int shipping_fee{calculate_shipping_fee(base_fee, surcharge)};
        total += shipping_fee;
    } // shipping_fee 的生命周期结束

    return total;
}
```

内部代码块结束时，`shipping_fee` 的生命周期已经结束，应付金额函数却还要执行 `return total;`。即使实现为整个函数预留了一份栈帧，这个局部对象也不会因此一直存活到函数返回。

实现可以在函数进入时一次预留所需的栈空间，但对象的生命周期仍按各自的初始化和代码块规则开始、结束。对象结束生命周期时，也不要求立即移动物理栈顶或清除原有字节；存储中残留相同数字不会延长对象的生命周期。

> [!IMPORTANT] 存储期、生命周期与物理存储位置
> **自动存储期约束的是对象所用存储的持续时间，不指定对象必须位于物理栈；对象生命周期按相应的初始化与销毁规则确定。**普通块局部对象可以在所属函数返回前结束生命周期。判断对象是否仍然存活，应依据语言规则，不能依据某个栈槽是否还存在或整份栈帧是否已经退去。

## 源码调用不保证对应真实栈帧

C++ 允许实现按照如同规则（as-if rule）改变内部执行方式，只要保留标准要求的可观察行为。比如开篇程序中的计算函数只处理这些整数，没有额外的输入输出；如果编译器能够确定结果，就可以化简计算，使 `main` 直接把 `115` 交给输出操作。

这时源码仍然用三个函数表达工作关系，机器代码却可能不再为两个计算函数发起独立调用。把被调用函数的工作合并进调用位置，通常称为内联展开（inlining）；内联后的计算还可以继续化简。某些满足条件的调用也可能复用调用资源，而不保留新的独立栈帧。

源码中仍然能够可靠推演的是：

```text
运费调用正常返回 15
    → 外层完成 shipping_fee 的初始化
    → total 从 100 变为 115
    → 外层返回，main 输出 115
```

> [!IMPORTANT] 源码调用与机器栈帧不保证一一对应
> **一次源码调用不保证对应一次实际机器调用或一份独立栈帧，多个源码对象也不保证各占一个固定栈槽。**实现可以内联、化简或复用调用资源，但必须保留语言要求的可观察行为。对象、调用和返回的语义应从源码规则判断，具体机器布局则要结合实际构建核对。

调试器（debugger）会尝试展示源码对应的调用与局部状态，但经过优化的程序可能无法完整呈现逐行对应的帧和对象。某些变量可能没有可供查看的独立存储，某些源码调用也可能已经合并；工具中的显示不足以单独证明语言上应有几份对象。

> [!TIP] 查询具体栈布局的依据
> 需要解释实际生成的汇编或调试器中的栈布局时，先确认目标架构与 ABI、编译器版本，以及优化和调试选项，再查该目标的调用约定并结合当前构建核对。寄存器分配、栈增长方向、对齐和具体偏移按这些条件查用；文末的 System V AMD64 ABI 与 Microsoft x64 文档分别是具体目标的查阅入口。

## 递归会受到实现资源限制

主线中的[递归求和](../05-nested-calls-and-independent-call-state.md#函数可以调用自身)会让同一个函数产生多层尚未结束的调用。若实现为每层保留独立栈帧，调用层数增加就会占用更多栈空间；是否能够省去或复用某些栈帧，取决于具体代码、实现与优化。

即使每层只使用几个整数，也不能仅根据这些整数的大小推算最大递归层数：实际栈帧还可能包含返回信息、保存的状态与平台要求的空间，调用链中的其他工作也会使用资源。C++ 没有规定适用于所有实现的最大递归层数，也没有规定栈资源耗尽时统一产生某个可捕获异常。

递归输入仍需满足原函数的数值和终止条件；调用栈模型帮助解释额外的实现资源需求，不能代替对这些语义条件的判断。
