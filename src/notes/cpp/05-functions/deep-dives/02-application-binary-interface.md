# 应用二进制接口：编译产物之间的契约（Application Binary Interface）

C++ 程序可以由多个源文件组成。每个源文件及其纳入的内容经过预处理与语言规定的转换后形成翻译单元（translation unit）；不同翻译单元可以分别编译为目标文件，再由链接器把这些编译产物组合起来。目标文件会用符号（symbol）标识可供其他编译产物引用的函数等实体；链接器能够根据符号把引用与定义对应起来，却不能重新按照 C++ 源码解释一次函数调用。

## 声明为什么不能单独决定二进制调用

假设函数定义位于 `pressure.cpp`：

```cpp
int calculate_operating_pressure_kpa(int measured_pressure_kpa, int margin_kpa) {
    return measured_pressure_kpa + margin_kpa;
}
```

另一个源文件 `control.cpp` 只保留函数声明，并在不知道函数体内容的情况下完成调用：

```cpp
int calculate_operating_pressure_kpa(int measured_pressure_kpa, int margin_kpa);

bool is_operating_pressure_valid() {
    return calculate_operating_pressure_kpa(240, 5) == 245;
}
```

C++ 语言规则能够判断声明与调用的类型是否匹配，并规定两个实参怎样初始化形参、函数怎样产生返回值。但两个源文件分别生成机器代码时，调用双方还必须对源码没有固定的实现问题作出相同判断：函数以什么符号进入目标文件，两个参数放在哪里，被调用函数从哪里取得它们，结果又通过什么位置交还给调用者。

声明建立了源码层面的函数契约；它不会独自决定这些机器层面的选择。如果调用双方作出不同选择，链接器即使找到了函数定义，也不能让这次调用自动恢复正确含义。

## ABI 固定分别编译边界

**应用二进制接口（Application Binary Interface，ABI）是分别编译的程序片段为了正确链接并协作而共同遵守的二进制契约。**它把语言标准留给实现选择的部分，收束为某个目标平台上的一致规则。

处理器提供一组能够直接保存运算状态的位置，称为寄存器（register）。机器代码还会用数值形式的机器地址（machine address）定位内存位置。某类数据或栈位置可能必须从满足特定地址边界的位置开始，这项要求称为对齐（alignment）。

ABI 中与函数调用有关的规则通常称为调用约定（calling convention）。**调用约定是 ABI 在函数调用边界上的一个组成部分，不等同于完整 ABI。**它可能规定：

- 参数按什么顺序进入哪些寄存器或栈位置；
- 返回结果由哪个寄存器或调用者提供的存储承载；
- 哪些寄存器必须在调用前后保持原有状态；
- 调用使用的栈位置需要满足怎样的对齐要求。

具体 ABI 可以让前几个整数参数进入寄存器，也可以让某些参数进入内存中的参数区域。选择本身不是当前模型的重点；真正的约束是调用者与被调用者必须遵循同一选择。如果调用者把参数放入寄存器，而被调用者却从另一处内存读取，源码中的类型完全一致也不能挽救这次调用。

## 同一契约还覆盖数据与链接边界

ABI 不只处理函数调用。一个目标平台上的完整二进制契约通常还需要让编译产物在以下边界作出一致判断：

| 边界 | 需要共同遵守的规则 |
| --- | --- |
| 函数调用 | 参数与返回结果的位置、寄存器状态和栈位置要求 |
| 数据 | 相关语言类型的具体大小、对齐和机器表示，以及对象布局（object layout） |
| 链接 | 源码名称怎样编码为目标文件符号、目标文件采用什么格式、怎样引用外部符号 |

对象布局描述一个对象占用多大的存储范围，以及各组成部分位于这段范围中的什么位置。本篇只建立需要协作的编译产物必须对此作出一致判断这一契约，不推导任何具体类型的布局。

源码名称编码为目标文件符号的过程常称为名称修饰（name mangling）。完整二进制契约通常由多份规范共同构成：目标平台的基础 ABI 负责寄存器使用、基本数据表示和目标文件等基础规则，C++ ABI 则补充名称修饰与 C++ 特有的对象布局等规则。关键不在于规则写入哪份文档，而在于需要协作的编译产物最终采用彼此兼容的选择。

## 语言、硬件、ABI 与工具链处在不同层次

| 层次 | 主要回答的问题 |
| --- | --- |
| C++ 标准 | 源程序必须呈现什么语义与可观察行为 |
| 指令集架构（Instruction Set Architecture，ISA） | 处理器提供哪些寄存器、机器指令与访问能力 |
| 目标 ABI | 编译产物怎样使用这些能力并彼此协作 |
| 编译器、汇编器与链接器 | 怎样按照语言规则和目标 ABI 生成、组合具体程序 |

某种指令集提供六十四位寄存器，不会自动决定某个 C++ 参数必须放入哪个寄存器；C++ 允许不同实现采用不同对象布局，也不表示同一程序的各个目标文件可以各自随意选择。目标 ABI 正是在这两层之间提供稳定契约。

ABI 也不是编译器品牌的别名。同一个编译器可以面向不同目标生成遵循不同 ABI 的代码；不同编译器面向同一目标时，也可能生成能够彼此链接的 ABI 兼容产物。编译目标、所选 ABI 与相关编译选项共同决定实际二进制边界。

## API 兼容不等于 ABI 兼容

应用程序接口（Application Programming Interface，API）描述源代码怎样使用一项功能。API 保持兼容，意味着使用方重新编译后仍能通过原来的声明使用它。ABI 兼容则要求已经编译的使用方不重新编译，仍能与新的二进制实现正确链接和运行。

改变函数参数类型、调用约定、二进制符号编码或对象布局，都可能破坏 ABI。某项修改即使没有改变源码中的函数名称，也不保证现有目标文件能够继续使用。如果所有相关源文件都按照彼此兼容的新规则重新编译，新的编译产物便能重新建立一致契约，此时不要求它与旧二进制保持兼容。

## 优化不取消真实的二进制边界

编译器能够把被调函数的工作合并进调用位置、消除局部对象，或直接化简某次调用，因此每条源码调用不一定都会形成可以观察到的 ABI 边界。只要程序中仍然存在需要实际协作的二进制边界，生成代码就必须遵循相应 ABI。

**ABI 约束的是实际存在的二进制协作边界，不要求编译器为源码中的每个抽象步骤保留固定机器结构。**实现方式可以变化，但需要保留的语言行为与外部二进制契约不能被破坏。

## 同一门 C++ 可以采用不同 ABI

Itanium C++ ABI 定义了名称修饰、数据布局等 C++ 特有的二进制规则，并与目标平台的基础 ABI 共同组成完整契约。以 Clang 为例，它的工具链文档列出了 libc++abi、libsupc++ 等可提供 Itanium C++ ABI 库部分的实现；具体目标实际采用哪套 ABI，仍取决于工具链配置与平台。MSVC 则使用其文档给出的 C++ 修饰名约定，并与 Windows 平台的调用约定和目标文件格式配合。这些工具链都能正确实现 C++，却不能仅凭源码都符合 C++ 就假定生成的二进制组件可以直接混合。
