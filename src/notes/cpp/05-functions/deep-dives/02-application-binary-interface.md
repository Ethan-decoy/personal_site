# 应用二进制接口：编译产物之间的契约（Application Binary Interface）

运费函数可以先编译好，调用它的代码再独立编译。调用位置有了正确声明，编译器就能检查实参和结果的用法；两个编译产物真正协作时，还需要对参数放在哪里、结果怎样交回、函数以什么符号被找到作出一致约定。

这些约定构成应用二进制接口（Application Binary Interface，ABI）。它让独立生成的代码能够正确衔接，也是复用目标文件、接入已编译的库或替换库版本时需要核对的边界。

## 声明为什么不能单独决定二进制调用

沿用运费计算，把实现与调用放进两个源文件。两个文件共同组成一份完整程序，金额按整数元记录，使用非负的小整数。

`shipping.cpp` 提供实现：

```cpp
int calculate_shipping_fee(int fee, int surcharge) {
    fee += surcharge;
    return fee;
}
```

`main.cpp` 在调用前提供声明：

```cpp
#include <iostream>

int calculate_shipping_fee(int fee, int surcharge);

int main() {
    int shipping_fee{calculate_shipping_fee(5, 10)};
    std::cout << shipping_fee << '\n'; // 15
    return 0;
}
```

每个源文件及其纳入的内容形成各自的翻译单元（translation unit）。按[分别编译的过程](../../00-introduction/03-source-file-to-executable.md#分别编译让翻译单元独立产生目标文件)，把两者编译为目标文件，再共同链接成程序，运行时输出 `15`：

```text
main.cpp     → main.o     ─┐
                          ├→ 可执行程序
shipping.cpp → shipping.o ─┘
```

这里先按通常的分别编译理解：编译 `main.cpp` 时没有运费函数体，也不进行跨翻译单元的联合优化。声明已经说明函数接收两个 `int` 并返回 `int`，足以检查 `5`、`10` 和 `shipping_fee` 的用法。

生成调用代码时，还必须确定这两个整数通过哪些机器位置交给实现；生成实现代码时，也必须从对应位置取得它们，并把结果 `15` 放回约定的位置。C++ 标准规定这次调用的语义，却没有为所有平台指定同一套寄存器、栈位置和二进制符号规则。调用双方需要在语言规则之外，共同采用目标平台的二进制约定。

## ABI 固定分别编译边界

> [!IMPORTANT] ABI 与调用约定的关系
> **ABI 是分别编译的程序片段为正确链接并协作而共同遵守的二进制契约。调用约定（calling convention）是其中规定参数、返回结果和调用状态怎样交接的部分。**源码声明提供名称和类型等使用信息；ABI 把相关实现选择收束为调用双方都遵守的规则，范围还包括数据与链接边界。

处理器直接用于保存运算中数据的位置称为寄存器（register）。机器代码也可以通过机器地址（machine address）定位内存位置。某类数据或栈区域的起始地址需要满足特定边界要求，称为对齐（alignment）。

对开篇的运费调用，调用双方需要对以下关系采用同一套约定：

| 需要交接的内容 | 调用方生成的代码 | 实现方生成的代码 |
| --- | --- | --- |
| 两个 `int` 参数 | 把 `5` 和 `10` 放到约定的寄存器或栈位置 | 从对应位置取得本次输入 |
| `int` 返回结果 | 从约定位置取得结果，用于初始化对象 | 把结果 `15` 交到约定位置 |
| 调用前后仍需保持的状态 | 按约定保存自己负责维持的状态 | 按约定维护或恢复自己负责的状态 |
| 栈空间的组织要求 | 提供自己负责的空间并满足对齐等要求 | 按相同的空间与对齐约定使用它 |

如果调用方按一种约定传入参数，实现方却按另一种约定取值，即使两边都把参数写成 `int`，也不能据此保证调用正确。寄存器与栈帧怎样共同保存状态，见[调用状态的实现方式](01-call-stack-and-stack-frames.md#栈帧承载一次活动调用的实现状态)。

## 同一契约还覆盖数据与链接边界

目标文件通过符号（symbol）记录可供其他编译产物引用的函数等实体。开篇的 `main.o` 引用运费函数，`shipping.o` 提供相应定义；链接过程需要把这项引用与实现对应起来。

源码名称编码为目标文件符号的过程常称为名称修饰（name mangling）。在常见的 C++ 名称修饰规则中，参数类型等信息也会参与编码，所以源码中看起来相同的函数名，不足以确定最终引用的是哪个二进制符号。

完整契约通常覆盖以下几类关系：

| 边界 | 需要共同遵守的规则 |
| --- | --- |
| 函数调用 | 参数与返回结果的位置、寄存器状态和栈位置要求 |
| 数据 | 边界两侧共同使用的类型大小、对齐、机器表示和对象布局（object layout） |
| 链接 | 名称怎样编码为符号、目标文件采用什么格式、怎样引用外部符号 |

对象布局描述对象占用多大的存储范围，以及各组成部分位于这段范围中的什么位置。边界两侧共同处理同一类数据时，需要对这些位置作出兼容判断，才能正确解释取得的数据。

完整二进制契约通常由多份规范共同构成。目标平台的基础 ABI 提供调用、基本数据表示和目标文件等规则，C++ ABI 再补充名称修饰与 C++ 特有的布局等约定；运行支持库（runtime library）和标准库也可能提供生成代码所需的实现。

> [!IMPORTANT] 符号匹配不能代替 ABI 兼容性判断
> **解析到一个符号，解决的是引用怎样找到实现的问题，不能单独证明调用、数据和运行支持约定都兼容。**符号不一致常表现为链接或加载失败；其他二进制约定不一致，也可能在符号已经匹配后仍导致错误。链接成功本身不是完整的兼容性证明。

## 语言、硬件、ABI 与工具链处在不同层次

| 层次 | 主要回答的问题 |
| --- | --- |
| C++ 标准 | 源程序必须呈现什么语义与可观察行为 |
| 指令集架构（Instruction Set Architecture，ISA） | 处理器提供哪些寄存器、机器指令与访问能力 |
| 目标 ABI | 编译产物怎样使用这些能力并彼此协作 |
| 编译器、汇编器与链接器 | 怎样按照语言规则和目标 ABI 生成、组合具体程序 |

硬件提供某组寄存器，不会自动决定某个 C++ 参数必须放入哪一个；语言允许实现选择布局，也不表示需要交换数据的编译产物可以各自采用互不兼容的布局。ABI 让调用双方对所用能力与数据表示采用一致的解释。

同一个编译器可以面向不同目标生成遵循不同 ABI 的代码；不同编译器在支持相同目标契约时，也可能生成能协作的产物。判断二进制边界时，需要确认实际编译目标、所选 ABI 与相关配置，编译器名称本身不能代替这些信息。

## API 兼容不等于 ABI 兼容

应用程序接口（Application Programming Interface，API）描述源代码怎样使用一项功能，包括公开声明及其行为约定。判断兼容性时，需要先明确保留的是调用源码，还是已经生成的二进制产物：

> [!IMPORTANT] API 兼容与 ABI 兼容的判断对象
> **API 兼容关注已有调用源码依据新版本的公开接口重新编译后，是否仍能按约定使用；ABI 兼容关注已有编译产物不重新编译时，是否仍能与新实现正确协作。**重新编译可以让调用方接受新的二进制规则，但不能据此证明旧产物也能继续使用。

例如，只把 `shipping.cpp` 中的定义替换为下面的等价实现，声明、计算规则和构建约定都保持一致：

```cpp
int calculate_shipping_fee(int fee, int surcharge) {
    return fee + surcharge;
}
```

这个改写保持本例的调用接口与结果。`main.cpp` 重新编译后仍能使用它；已经生成的 `main.o` 也可以与重新编译的实现共同链接，仍然输出 `15`。

再考虑接口变化：把第一个参数从 `int` 改成 `long`，同步修改声明与实现，并保持小整数费用的计算含义。调用源码中的 `calculate_shipping_fee(5, 10)` 可以依据新声明完成 `int` 到 `long` 的转换，重新编译后仍可使用这次调用。

但旧 `main.o` 已经按原来的 `int` 参数版本生成引用。在常见 C++ 名称修饰规则下，这个参数类型变化会改变函数符号；如果新实现只提供 `long` 版本，旧引用就失去了对应定义，通常会在链接时失败。

| 对本例的修改 | 保留调用源码，按新声明重新编译 | 保留旧 `main.o`，不重新编译 |
| --- | --- | --- |
| 只等价改写函数体，保留接口和构建约定 | 仍可使用 | 仍可与新实现协作 |
| 首个参数改为 `long`，不再提供原 `int` 版本 | 本例的小整数调用仍可成立 | 在上述名称修饰条件下，旧引用找不到原版本 |

这张表针对本例的调用与给定修改，不把某一次调用仍可编译扩大为对整个 API 的兼容承诺。如果所有相关源文件都依据新的正确声明和兼容配置重新编译，新产物可以建立一致契约；是否还支持旧产物，是另一项需要单独核对的要求。

## 优化不取消真实的二进制边界

普通分别编译时，`main.o` 没有运费函数体，需要通过保留的函数边界与实现协作。在能够联合分析调用方与实现方的构建中，编译器也可能把工作合并进调用位置、化简计算或改写内部调用，因此源码调用未必留下独立的机器调用。

> [!IMPORTANT] ABI 约束保留下来的独立协作边界
> **ABI 约束独立编译产物之间仍需保留的二进制协作边界，不要求每次源码调用都对应固定的机器结构。**内部实现可以优化；仍需对独立使用方提供的接口，则必须维持承诺的二进制契约。

判断优化结果时，先确认需要保留哪些对外接口，再观察内部调用是否被合并或化简。某个构建里恰好省去了一次调用，并不证明该接口对其他独立使用方也可以随意改变。

## 同一门 C++ 可以采用不同 ABI

Itanium C++ ABI 定义了名称修饰、数据布局及相关运行支持等 C++ 二进制规则，并与采用它的目标平台基础 ABI 配合。Microsoft 的 C++ 修饰名约定与 Windows 调用约定则构成另一组具体规则。这些文档说明的是特定契约，C++ 标准本身没有把所有实现统一为同一种 ABI。

生成的代码还可能依赖标准库与运行支持库；后者为生成代码提供所需的支持操作。这些库采用的接口、版本与构建配置，也可能影响边界兼容性。仅确认函数名或处理器架构相同，仍不足以完成核对。

> [!TIP] 接入已编译组件时的查阅依据
> 使用预编译库或替换库版本前，核对目标架构与操作系统、所用 ABI、编译器及库的兼容性说明，以及影响边界的构建选项。需要追踪参数、符号或布局时，分别查目标调用约定、C++ ABI 和库的版本文档，再结合实际产物核对。文末文档是具体平台与工具链的入口，不是一套通用于所有 C++ 实现的固定取值表。
