# 应用二进制接口：编译产物之间的契约（Application Binary Interface）

C++ 程序可以由多个源文件组成。每个源文件能够先被独立编译（separate compilation）为目标文件，再由链接器把这些编译产物组合起来。链接器可以根据符号找到函数定义，却不能重新按照 C++ 源码解释一次函数调用；调用双方必须已经对二进制层面的协作方式作出相同判断。

## 源码声明只能建立语言契约

假设函数定义位于 `pressure.cpp`：

```cpp
int calculate_operating_pressure_kpa(int measured_pressure_kpa, int margin_kpa) {
    return measured_pressure_kpa + margin_kpa;
}
```

另一个源文件 `control.cpp` 只保留函数声明，并在不知道函数体内容的情况下完成调用：

```cpp
int calculate_operating_pressure_kpa(int measured_pressure_kpa, int margin_kpa);

bool is_operating_pressure_valid() {
    const int operating_pressure_kpa{calculate_operating_pressure_kpa(240, 5)};
    return operating_pressure_kpa == 245;
}
```

C++ 语言规则能够判断声明与调用的类型是否匹配，并规定两个实参怎样初始化形参、函数怎样产生返回值。但两个源文件分别生成机器代码时，还必须共同回答源码没有固定的实现问题：函数以什么二进制名称进入目标文件，两个参数放在哪里，被调用函数从哪里取得它们，结果又通过什么位置交还给调用者。

## ABI 固定编译产物之间的协作方式

**应用二进制接口（Application Binary Interface，ABI）是编译后的程序片段、库与运行时之间共同遵守的二进制契约。**它把语言标准留给实现选择的部分，收束为某个目标平台上的一致规则。

函数调用相关的 ABI 规则通常称为调用约定（calling convention），可能规定：

- 参数按什么顺序进入哪些寄存器或栈位置；
- 返回结果由哪个寄存器或调用者提供的存储承载；
- 哪些寄存器必须在调用前后保持原值；
- 调用过程中栈指针需要满足什么对齐。

具体 ABI 可以让前几个整数参数进入寄存器，也可以让某些参数进入内存中的参数区域。选择本身不是当前模型的重点；真正的约束是调用者与被调用者必须遵循同一选择。如果调用者把参数放入寄存器，而被调用者却从另一处内存读取，源码中的类型完全一致也不能挽救这次调用。

## ABI 还约束数据与链接边界

ABI 不只处理函数调用。一个完整的目标平台 ABI 通常还会约束：

- 语言类型在特定目标上的具体大小、对齐和机器表示；
- 源码中的外部函数名称怎样编码成目标文件中的符号，这项过程常称为名称修饰（name mangling）；
- 目标文件采用的格式，以及编译产物怎样引用外部符号；
- 某些语言运行时机制怎样跨越已经编译的函数边界。

这里的对齐是指数据或栈位置的起始地址必须满足某种边界条件。这些规则可能由平台 ABI、处理器架构 ABI 与 C++ ABI 等多份规范共同构成，而不是全部来自一份文档。对调用者而言，重要的是整套工具链最终选择了哪一组相互兼容的规则。

## 语言、硬件、ABI 与工具链处在不同层次

| 层次 | 主要回答的问题 |
| --- | --- |
| C++ 标准 | 源程序必须呈现什么语义与可观察行为 |
| 指令集架构（Instruction Set Architecture，ISA） | 处理器提供哪些寄存器、机器指令与访问能力 |
| 目标 ABI | 编译产物怎样使用这些能力并彼此协作 |
| 编译器与链接器 | 怎样按照语言规则和目标 ABI 生成、组合具体程序 |

硬件拥有六十四位寄存器，不会自动决定某个 C++ 参数必须放入哪个寄存器；C++ 允许不同实现采用不同对象布局，也不表示同一程序的各个目标文件可以各自随意选择。目标 ABI 正是在这两层之间提供稳定契约。

ABI 也不是编译器品牌的别名。同一个 Clang 可以面向 Windows x64、Linux x86-64 或 AArch64 生成遵循不同 ABI 的代码；GCC 与 Clang 面向同一目标时，也可能生成能够彼此链接的 ABI 兼容产物。编译目标、所选 ABI 与相关编译选项共同决定实际二进制边界。

## API 兼容不等于 ABI 兼容

应用程序接口（Application Programming Interface，API）描述源代码怎样使用一项功能。API 保持兼容，意味着使用方重新编译后仍能通过原来的声明使用它。ABI 兼容则要求已经编译的使用方不重新编译，仍能与新的二进制实现正确链接和运行。

改变函数参数类型、调用约定、二进制符号编码或对象布局，都可能破坏 ABI。某项修改即使没有改变源码中的函数名称，也不保证现有目标文件能够继续使用。反过来，只要所有相关源文件一起重新编译，新的编译产物可以重新建立一套一致契约，此时并不要求它与旧二进制保持兼容。

**C++ 标准一致只说明源码遵循同一门语言；二进制能否直接协作，还取决于各方是否遵循兼容的 ABI。**

## 优化不取消真实的二进制边界

编译器能够内联函数、消除局部对象，或直接化简某次调用，因此每条源码调用不一定都会形成可以观察到的 ABI 边界。只要调用必须跨越独立编译且不能被整体消除的程序片段，生成代码仍需遵循相应 ABI。

ABI 约束的是需要实际协作的二进制边界，不要求编译器为源码中的每个抽象步骤保留固定机器结构。这与 C++ 的如同规则一致：实现方式可以变化，但需要保留的语言行为与外部二进制契约不能被破坏。

## 常见的 C++ ABI

Itanium C++ ABI 定义了名称修饰、数据布局等 C++ 特有的二进制规则。名称保留了最初面向 Itanium 处理器的历史，但这套 ABI 后来被许多其他架构上的 GCC 与 Clang 工具链采用。它还需要结合目标平台的基础 ABI，才能得到寄存器使用、基本类型大小等完整规则。

Windows 上的 MSVC 工具链采用另一套 C++ ABI，并与 Windows 平台调用约定和对象文件格式配合。二者都可以正确实现 C++，却不因此保证彼此生成的 C++ 二进制组件能够直接混合。
