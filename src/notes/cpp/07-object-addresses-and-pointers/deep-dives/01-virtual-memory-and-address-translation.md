# 虚拟内存与地址转换（Virtual Memory and Address Translation）

[返回对象、存储与地址](../01-objects-storage-and-addresses.md)

在采用分页虚拟内存的常见桌面和服务器系统中，程序使用的地址通常属于当前进程的虚拟地址空间，而不是直接表示某个物理内存位置。操作系统负责建立映射，处理器的内存管理单元借助转换缓存与页表完成地址转换。

这层间接关系并不是单纯绕远。它把复杂且可能不连续的物理内存隐藏在进程地址空间之后，使系统能够隔离进程、按页控制权限、受控共享存储，并只在真正需要页面时准备物理资源。

## 直接使用物理地址的问题

如果用户程序直接把自己使用的每个地址当作物理地址，不同程序就会共享同一套位置编号：

```text
程序 A 使用地址 0x1000 ──→ 物理地址 0x1000
程序 B 使用地址 0x1000 ──→ 物理地址 0x1000
```

两个程序会争用同一位置。错误的地址计算也可能越过程序边界，直接破坏另一个程序或操作系统的数据。

物理内存还会随着程序装入、退出和分配而形成分散的可用区域。若程序要求一段连续地址，直接寻址模型就需要找到同样连续的物理存储；程序被装入不同位置时，内部地址也可能需要随之调整。

虚拟内存把程序使用的位置编号与实际物理位置分开：

```text
进程 A：虚拟地址 0x1000 ──→ 物理页框 42
进程 B：虚拟地址 0x1000 ──→ 物理页框 913
```

两个进程都能使用虚拟地址 `0x1000`，但它们的映射彼此独立。虚拟地址相同不再意味着物理位置相同。

## 分页地址模型

分页（paging）把虚拟地址空间和物理地址空间分别划分为固定大小的区域。虚拟地址一侧称为虚拟页（virtual page），物理内存一侧对应物理页框（physical frame）。

在页面大小为 $2^p$ bytes 的基本模型中，虚拟地址可以拆成两部分：

```text
虚拟地址
┌──────────────────────┬──────────────────┐
│ 虚拟页号 VPN         │ 页内偏移 offset  │
└──────────────────────┴──────────────────┘
```

虚拟页号（Virtual Page Number, VPN）标识虚拟页，页内偏移（page offset）标识目标字节在该页中的位置。页表把 VPN 转换为物理页框号（Physical Frame Number, PFN），页内偏移保持不变：

```text
VPN ──页表──→ PFN

虚拟地址 = VPN × 页面大小 + offset
物理地址 = PFN × 页面大小 + offset
```

假设当前页面大小为 4 KiB，也就是 `0x1000` bytes，虚拟地址 `0x1234` 可以拆成：

```text
虚拟页号：0x1
页内偏移：0x234
```

若页表把虚拟页 `0x1` 映射到从物理地址 `0x5A000` 开始的页框，最终地址就是：

```text
物理页框起始地址：0x5A000
页内偏移：        0x00234
最终物理地址：    0x5A234
```

4 KiB 是常见页面大小，不是跨平台固定值。处理器还可能支持多种页面大小，因此具体的地址拆分必须由目标架构和系统配置确定。

## 页表与分散的物理存储

页表（page table）是描述虚拟页映射关系的数据结构。叶级页表项（Page Table Entry, PTE）通常记录物理页框以及与访问有关的属性：

```text
虚拟页号
    ↓
页表项
    ├─ 物理页框号
    ├─ 是否存在有效映射
    ├─ 读写与执行权限
    └─ 其他架构相关状态
```

连续虚拟页不必映射到连续物理页框：

```text
虚拟页 10 ──→ 物理页框 81
虚拟页 11 ──→ 物理页框 7
虚拟页 12 ──→ 物理页框 203
```

程序看到的三个页面仍然连续。跨过虚拟页边界时，处理器改用下一项映射，物理位置是否相邻不会改变程序对连续地址的使用。

现代地址空间很大，如果为每个可能的虚拟页都预先建立一个平坦表格，页表本身会消耗大量内存。因此常见架构使用多级页表（multi-level page table）：虚拟地址的高位依次索引不同层级，只为实际使用的地址范围准备必要的表。

多级结构和层数属于具体架构。大页还可能使较高层级的表项直接成为最终映射，因此不能把“每次转换必然经过固定层数”写成通用规则。

## MMU 与 TLB

内存管理单元（Memory Management Unit, MMU）是处理器中执行或参与地址转换与权限检查的硬件。页表通常位于内存中，由操作系统维护；MMU 在需要时读取这些表。

如果每次内存访问都重新遍历多级页表，一次普通读取就可能额外产生多次内存访问。处理器因此使用转换后备缓冲区（Translation Lookaside Buffer, TLB）缓存近期使用的地址翻译：

```text
虚拟地址
    ↓
查询 TLB
    ├─ 命中：直接得到已缓存的页框与权限
    └─ 未命中：执行页表遍历或架构规定的 refill
                         ↓
                    更新 TLB
```

TLB 缓存的是地址翻译及相关属性，不是对象数据，也不是页表本身。数据缓存负责缓存内存内容，TLB 则减少重复查询地址映射的成本。

具体补充 TLB 的方式依架构而定。一些处理器能够硬件遍历页表，另一些架构允许软件参与转换补充（refill）；因此“每次 TLB 未命中都由硬件静默完成”也不是通用保证。

## TLB 未命中与页异常

TLB 未命中（TLB miss）和页异常（page fault）描述的是不同问题：

| 事件 | 表示什么 | 可能的结果 |
| --- | --- | --- |
| TLB 未命中 | TLB 中没有当前访问可用的缓存翻译 | 查询页表；映射有效且权限允许时，填充 TLB 后继续 |
| 页异常 | 当前页表状态或权限不能直接完成访问 | 操作系统可能补齐映射后重试，也可能判定访问非法 |

TLB 未命中只说明缓存里没有答案。如果页表中存在有效映射，处理器取得映射后仍可正常完成访问，不需要把错误报告给程序。

页异常也不等于程序一定崩溃。第一次访问尚未实际分配物理页的虚拟地址、装入文件映射内容或处理写时复制，都可以故意借助页异常让操作系统介入。内核完成相应工作后，原来的指令可以重新执行。

只有当访问无法被合法处理，例如地址没有有效映射或违反访问权限时，操作系统才会把错误进一步报告给进程。不同系统采用的异常和进程级通知形式并不相同。

## 按需分页

按需分页（demand paging）表示系统等到页面真正被需要时，再让它进入可使用或驻留状态。程序获得一段虚拟地址范围，并不意味着每个页面已经立即占用物理内存。

一次能够被正常处理的页异常可能对应：

- 第一次访问匿名内存，系统提供清零后的物理页；
- 第一次访问文件映射，从后备文件取得内容；
- 写入采用私有映射语义的共享物理页，为当前进程建立副本；
- 先前换出的页面重新进入物理内存。

交换（swapping）只是其中一种可能情况。按需分页不等于“用磁盘假装内存”，页异常也不表示一定发生磁盘访问。

## 页面权限

页表项除了记录地址映射，还可以携带访问属性。常见属性包括：

- 可读；
- 可写；
- 可执行；
- 用户态是否允许访问。

处理器在转换地址时同时检查这些属性。代码页面可以被映射为可读、可执行而不可写，普通数据页面可以可读、可写而不可执行，完全未映射的保护页则可以用于发现越界访问。

页面权限通常作用于整个页面或映射区域，不是为每个 C++ 对象单独设置。它也不同于 C++ 的 `const`：`const` 是语言类型与修改规则，页面只读是操作系统和硬件实施的访问权限。实现可以把某些对象放入只读区域，但 C++ 不保证每个 const 对象都占有物理只读页面。

## 共享映射与写时复制

虚拟地址映射不要求不同虚拟页一定对应不同物理页。系统可以让多个进程的虚拟页映射同一个物理页：

```text
进程 A：虚拟页 20 ─┐
                    ├──→ 同一个物理页框
进程 B：虚拟页 61 ─┘
```

共享库、共享内存和内存映射文件都可以利用这种关系。两个进程中的虚拟地址可以不同，共享的是它们最终映射到的存储。

写时复制（copy-on-write）则让多个映射先共享同一页面，并暂时禁止直接写入。某个进程第一次尝试修改时触发页异常，操作系统复制该页面，再把写入方的映射改到新副本：

```text
写入以前：进程 A ─┐
                  ├──→ 共享物理页
          进程 B ─┘

进程 A 首次写入以后：
          进程 A ───→ 新复制的物理页
          进程 B ───→ 原来的物理页
```

写时复制是一种常见实现技术，不是 C++ 指针自身具有的能力。操作系统接口可以规定私有修改的可观察语义，但具体是否采用写时复制仍属于平台实现。

## 多个映射与并行执行

多个虚拟地址映射同一个物理页框，不会造成地址转换上的歧义。转换的输入不仅包括虚拟地址，还处于当前进程的地址空间上下文中；处理器查询的是当前上下文对应的映射，而不是拿物理地址反向寻找唯一的虚拟地址：

```text
进程 A 的映射：虚拟页 20 ──→ 物理页框 8
进程 B 的映射：虚拟页 61 ──→ 物理页框 8
```

执行进程 A 的核心使用第一项映射，执行进程 B 的核心使用第二项映射。两项得到同一个物理页框是允许且有意建立的结果。

两个进程仍然可以在不同处理器核心上同时运行。它们的计算、控制流以及对其他存储的访问彼此独立；只有真正访问共同映射的存储时，内存系统才需要协调相应请求。

共享一个物理页也不表示双方必然访问同一个数据。一个页面包含许多字节，两个进程可以读取同一页面中的不同位置。真正需要程序协调的是对同一份共享状态进行写入，尤其是同时修改同一位置。

## 缓存一致性

处理器通常不会让每次读取都直接到达物理内存，而是以缓存行（cache line）为单位把近期数据保存在各级数据缓存中。多个核心读取同一物理位置时，各自缓存中可以同时存在该缓存行的副本。

在主流缓存一致多处理器系统中，缓存一致性协议（cache coherence protocol）负责协调这些副本。以常见的失效式协议为例，两个核心开始时都可以缓存值 `42`：

```text
核心 A 的缓存行：42，可共享读取
核心 B 的缓存行：42，可共享读取
```

核心 A 准备写入 `43` 时，需要先取得该缓存行的写入所有权。协议会使核心 B 中的旧副本失效：

```text
核心 A 写入 43
      ↓
核心 A 取得缓存行的写入所有权
      ↓
核心 B 中保存 42 的副本失效
```

核心 B 不会因此自动执行一次读取，也不一定立即收到新值。等它以后再次加载这个位置时，失效的缓存行不能继续使用，于是需要通过缓存层级或一致性互连取得当前内容。最新数据可能直接来自另一个核心的缓存，并不要求先写回物理内存。

MESI 以 Modified（已修改）、Exclusive（独占）、Shared（共享）和 Invalid（无效）四种状态命名；它及其变体是这类协议的常见实现，但不是 C++ 或所有处理器平台的统一要求。非一致缓存、某些设备访问和部分嵌入式环境可能需要平台规定的显式缓存维护操作。

## 两种缓存未命中

TLB 和数据缓存保存的是不同信息，因此“缓存未命中”必须说明缺少什么：

| 事件 | 缓存的内容 | 未命中后的目标 |
| --- | --- | --- |
| TLB 未命中 | 虚拟页到物理页框的地址翻译及属性 | 查询页表或执行架构规定的 refill |
| 数据缓存未命中（data-cache miss） | 某个物理地址范围对应的缓存行内容 | 从其他缓存层级、另一核心或内存系统取得数据 |

一方写入共享缓存行并使另一方的旧副本失效后，另一方下一次读取通常遇到的是数据缓存未命中。原有虚拟页映射可能完全没有变化，因此不必同时发生 TLB 未命中，更不等于发生页异常。

反过来，TLB 未命中只表示地址翻译缓存中没有答案；页表遍历完成后，随后对数据缓存的查询仍是另一件事。地址翻译与数据取得在概念上属于不同阶段，具体微架构可以让部分工作并行或推测执行，不能把它们画成所有处理器都严格串行的固定时序。

## 共享不等于同步

缓存一致性保证的重点，是避免不同核心长期把互相矛盾的缓存副本同时当作同一位置的当前内容。它不会自动规定应用中的多步操作应当按照什么业务顺序执行。

例如，共享计数器初始为 `0`，两个执行者都进行“读取、加一、写回”：

```text
进程 A 读取 0
进程 B 读取 0
进程 A 写入 1
进程 B 写入 1
```

每次单独写入都可以经过缓存一致性协议传播，但最终结果仍可能是 `1`，而不是 `2`。问题不在于缓存永久保存了两个不同版本，而在于完整的读取—修改—写入没有被当作一个不可分割的操作。这称为丢失更新（lost update）。

这个过程只用于说明丢失更新的逻辑来源。若多个 C++ 线程无同步地冲突访问同一个普通对象，程序已经产生数据竞争（data race），行为未定义，不能把“最终得到 `1`”理解成标准承诺的结果范围。即使使用原子对象（atomic object），把一次更新拆成彼此独立的读取和写入也仍可能丢失更新；完整状态转移需要原子读—改—写（atomic read-modify-write）操作或互斥保护。

同样，一方依次写入数据和“数据已经准备好”的标记，也不能仅凭缓存一致性就推导另一方一定按照源码顺序观察到这两个变化。编译器和处理器可能按照语言与平台允许的规则调整普通内存操作，写缓冲等结构也会影响变化何时对其他核心可见。

三个层次需要分别处理：

| 层次 | 解决的问题 |
| --- | --- |
| 共享映射 | 双方怎样访问同一份物理存储 |
| 缓存一致性 | 各核心怎样维护同一缓存行的协调副本 |
| 同步机制 | 读写何时发生、按照什么顺序被观察，以及复合操作是否不可分割 |

真正的跨进程可写共享需要操作系统和平台支持的进程间同步机制。C++ 标准不定义操作系统进程和共享映射接口，因此把原子对象放入进程共享区域后能否提供跨进程保证，也必须服从目标实现与平台文档。

`volatile` 不能替代这种同步。它具有自己的语言用途，但不自动提供跨执行者的原子性、操作顺序或进程间协调。

写时复制采用了不同策略：第一次写入后，写入方映射到独立物理副本，另一方继续映射原页面。双方此后不再修改同一份物理存储，因此也不会自动观察彼此对各自副本的修改。

## 缓存行与伪共享

页面是地址映射和权限管理的常见粒度，缓存一致性通常以更小的缓存行为粒度。两个数据即使位于同一物理页，也可能处在不同缓存行中，彼此写入不必争夺同一缓存行。

反过来，两个彼此独立的数据可能恰好位于同一缓存行。不同核心分别修改它们时，虽然没有共同修改同一个对象，整个缓存行仍可能反复转移写入所有权：

```text
同一缓存行
┌──────────────────┬──────────────────┐
│ 进程或核心 A 的数据 │ 进程或核心 B 的数据 │
└──────────────────┴──────────────────┘
```

这种现象称为伪共享（false sharing）。它通常表现为性能下降，而不是两个独立数据在语言意义上突然变成同一个对象。是否发生以及代价多大，取决于缓存行大小、数据布局和具体硬件。

## 地址空间布局随机化

地址空间布局随机化（Address Space Layout Randomization, ASLR）会改变进程虚拟地址空间中若干区域的位置，例如主程序、共享库、映射区域、栈或堆的起始位置。

因此，同一程序在不同运行中创建相似对象，也可能观察到不同的虚拟地址。ASLR 随机化的是虚拟地址空间布局，不是把每个虚拟地址随机转换到物理位置。

ASLR 用于增加依赖固定地址的攻击难度，属于概率性的安全缓解。它不提供进程隔离本身，也不能保证地址信息永远无法泄漏。

## 无 MMU 的系统

分页虚拟内存不是 C++ 程序运行的必要条件。一些嵌入式处理器没有 MMU，程序地址可以更直接地对应平台物理地址空间；另一些系统使用内存保护单元（Memory Protection Unit, MPU）按区域检查权限，但不通过页表把虚拟页翻译成物理页框。

无 MMU 不表示完全没有地址管理，也不能推导出所有嵌入式系统都没有虚拟内存。嵌入式平台范围很广，部分处理器和操作系统同样支持完整 MMU。

只有确认目标平台采用分页地址转换后，VPN、页表、TLB 与页异常这套模型才适用。具体平台的内存映射必须以处理器手册、ABI 和操作系统文档为准。

## 与 C++ 指针的边界

C++ 定义的是抽象机中的对象、存储和指针语义，不要求执行环境具有操作系统、MMU、页表或虚拟地址：

| C++ 可以保证的语言关系 | 常见平台的实现方式 |
| --- | --- |
| 对象占用存储区域 | 存储可能由虚拟页面映射到物理页框 |
| 指向对象的指针值表示对象所占存储首字节的地址 | 指针的位模式通常参与当前进程的虚拟寻址 |
| 指针类型与整数类型不同，指针表示由实现定义 | 常见调试器把指针显示为十六进制虚拟地址 |
| 实现必须保持抽象机规定的可观察行为 | 编译器可以消除不影响可观察行为的对象或内存访问 |

因此，不能把打印出的指针值一概称为物理地址，也不能认为每次源码中的解引用都必然执行一次页表遍历。对于采用分页虚拟内存的常见系统，更接近实际的模型是：

```text
C++ 对象指针
      ↓
当前进程中的虚拟地址
      ↓
MMU：TLB 与页表
      ↓
物理页框中的位置
```

这张图描述的是常见实现路径。C++ 源码的正确性仍应建立在对象生命周期、指针有效性和语言允许的访问规则上，而不是建立在某次运行观察到的虚拟地址布局上。
