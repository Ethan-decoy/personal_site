# 对象布局、对齐与填充（Object Layout, Alignment, and Padding）

结构体正文已经能够根据类型、对象和成员名称判断程序语义。实现真正为对象安排存储时，还必须把每个成员落实到从对象起始地址算起的具体位置。对象布局（object layout）就是从成员语义通往实际存储的这层映射。

## 语言只规定部分布局约束

```cpp
struct sensor_sample {
    char status_code;
    int pressure_kpa;
    char quality_code;
};
```

C++ 能够确定每个 `sensor_sample` 对象包含三个相应的成员子对象。对于当前三个具有相同访问权限、大小非零的普通成员，后声明成员具有更高地址；聚合初始化仍按声明顺序匹配初始化器。

这些规则没有固定 `int` 必须占 4 bytes，也没有直接给出 `pressure_kpa` 位于偏移 `4`、完整对象占用 `12` bytes。实现还要结合目标平台允许的类型大小、对齐要求与 ABI 规则，选择满足语言约束的一种具体布局。

## 为什么平台会为对象类型规定对齐

从程序的地址模型看，内存位置可以按 byte 区分；处理器执行加载与存储时，却经常用一条指令在寄存器与内存之间移动多个 bytes。多 byte 数据从适合该访问宽度的边界开始时，处理器通常可以用更直接的方式完成访问。

数据从任意 byte 地址开始时，一次访问可能跨越处理器内部的数据边界，需要拆成多次传输再组合结果。不同架构与不同指令对此没有统一行为：有些能够处理未对齐访问但可能付出额外代价，有些访问形式则会产生硬件故障。

为了看清“跨越边界”的含义，可以设想一台按四字节单元完成自然传输的简化机器：

```text
地址偏移：  0   1   2   3 │ 4   5   6   7
传输单元：┌───────────────┐┌───────────────┐
          │    第 1 单元   ││    第 2 单元   │
          └───────────────┘└───────────────┘
```

从偏移 `0` 开始读取 4 bytes，数据全部落在第一个单元中；从偏移 `1` 开始读取 4 bytes，所需数据却同时落在两个单元中。后者可能需要两次传输、移位与组合。真实处理器的总线、缓存与指令行为远比这张图复杂，这个假设只解释对齐为什么可能影响访问方式，并不规定所有处理器都按四字节单元工作。

目标平台会据此为不同类型选择稳定的地址要求。对齐不是为了让字节图看起来整齐，也不是编译器无理由浪费空间；它把机器访问能力与平台约定转化为对象类型必须满足的地址契约。

## 对齐值约束对象的起始地址

C++ 中的每种对象类型都有对齐要求（alignment requirement）。对齐值描述这种对象的起始地址必须满足怎样的边界条件；`alignof(T)` 产生完整对象类型 `T` 的对齐要求。

有效对齐值是 2 的整数次幂。若当前实现规定：

```text
alignof(int) == 4
```

那么在本章采用的常见按 byte 编址模型中，可以把合法地址理解为满足：

```text
object_address % 4 == 0
```

因此，从对齐条件看，`0x1000`、`0x1004` 和 `0x1008` 都满足这种 `int` 对象的起始地址要求，`0x1001` 则不满足。地址满足对齐只是建立对象的必要条件之一；相应存储必须存在，对象的生命周期也必须已经开始。对齐为 `4` 只约束起始地址，不表示对象一定占 4 bytes，也不表示处理器的缓存单位只有 4 bytes。

无论某个处理器能否碰巧执行未对齐的机器指令，C++ 对象都必须建立在满足其类型对齐要求的存储中。**硬件能否完成一次未对齐访问，与 C++ 程序是否满足对象的对齐要求，是两个不同层次的问题。**

## ABI 怎样让独立编译的代码共享布局

第五章的[应用二进制接口：编译产物之间的契约](../../05-functions/deep-dives/02-application-binary-interface.md)已经建立了 ABI 的通用模型。本篇只使用其中与数据布局有关的部分：分别编译的程序片段必须对类型大小、对齐和成员偏移作出相同判断。

| 层次 | 在对象布局中负责什么 |
| --- | --- |
| C++ 标准 | 规定对象必须满足类型对齐，定义 `sizeof`、`alignof` 及成员顺序的语言约束 |
| 处理器与内存系统 | 提供实际加载、存储能力，并决定不同地址访问的硬件限制与代价 |
| 目标 ABI | 规定二进制边界需要共同遵守的类型大小、对齐、成员偏移与完整对象布局规则 |
| 编译器与编译选项 | 按照语言规则和所选 ABI 生成具体布局与机器指令 |

编译器处理 `sample.pressure_kpa` 时，可以把成员访问变成“对象起始地址加固定偏移处的一次 `int` 访问”。普通加载与存储指令不需要在运行时重新查找成员名称。

如果一份目标文件认为 `pressure_kpa` 位于偏移 `4`，另一份目标文件却按偏移 `8` 写入同一个结构体，两边即使使用相同的 C++ 类型名称，也会访问不同 bytes。ABI 的数据布局规则使独立编译的代码对以下数字达成一致：

- 每种相关类型的大小；
- 完整对象需要满足的对齐；
- 每个成员相对对象起始地址的偏移；
- 完整对象在连续存储中的跨度。

**ABI 不是 C++ 语义的替代品；它把标准允许存在的实现选择，固定为特定目标上的共同二进制契约。**

## 从地址约束推导内部填充

下面只分析一个明确的目标假设：

| 类型 | `sizeof` | `alignof` |
| --- | ---: | ---: |
| `char` | 1 | 1 |
| `int` | 4 | 4 |

再假设 `sensor_sample` 对象从满足四字节对齐的地址 `0x1000` 开始。布局过程按照成员声明顺序，为每个成员寻找不早于当前末尾、同时满足该成员对齐要求的第一个地址。

`status_code` 的对齐为 `1`，可以直接位于 `0x1000`，占用这一个 byte。放置完成后，下一个候选地址是 `0x1001`。

`pressure_kpa` 需要四字节对齐，但候选地址不满足要求：

```text
0x1001 % 4 != 0
```

第一个不早于 `0x1001` 且满足要求的地址是 `0x1004`：

```text
0x1004 % 4 == 0
```

因此偏移 `1～3` 被跳过，`pressure_kpa` 位于偏移 `4～7`。最后的 `quality_code` 只要求一字节对齐，可以紧接着位于偏移 `8`。

| 成员 | 大小 | 对齐 | 直接候选偏移 | 实际偏移 | 前置填充 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `status_code` | 1 | 1 | 0 | 0 | 0 |
| `pressure_kpa` | 4 | 4 | 1 | 4 | 3 |
| `quality_code` | 1 | 1 | 8 | 8 | 0 |

成员之间为了让后续成员满足对齐而留下的区域称为内部填充（internal padding）。这里的三个填充 bytes 属于完整 `sensor_sample` 对象占用的存储，却不属于前后任何一个成员子对象。

## 尾部填充让对象跨度可以重复

当前目标 ABI 让 `sensor_sample` 采用其最严格普通成员所需的四字节对齐。最后一个成员位于偏移 `8` 并占用一个 byte，所以全部成员在偏移 `9` 处结束。

若完整对象大小直接取 `9`，紧随其后的同类型对象将从下面的地址开始：

```text
0x1000 + 9 == 0x1009
0x1009 % 4 != 0
```

第二个对象的起始地址无法满足 `sensor_sample` 的四字节对齐。把第一个对象的存储跨度补到 `12` 后，新的起点变成：

```text
0x1000 + 12 == 0x100C
0x100C % 4 == 0
```

偏移 `9～11` 因此成为尾部填充（tail padding）。对于当前普通 `sensor_sample` 完整对象，这三个 bytes 计入 `sizeof(sensor_sample)`，使同类型对象连续放置时仍然满足对齐。

```text
对象 1：0x1000                                             0x100B
        ┌─────────────┬──────────┬──────────────┬──────────────┬──────────┐
        │ status_code │ 填充 3 B │ pressure_kpa │ quality_code │ 填充 3 B │
        └─────────────┴──────────┴──────────────┴──────────────┴──────────┘

对象 2：0x100C
        └── 再次满足四字节对齐
```

**内部填充让成员子对象满足各自的对齐；尾部填充让完整对象的存储跨度能够重复排列，同时仍满足完整类型的对齐。**

## sizeof、alignof 与成员偏移回答不同问题

在当前明确假设下，可以得到：

```text
sizeof(sensor_sample)  == 12
alignof(sensor_sample) == 4

status_code   的偏移 == 0
pressure_kpa  的偏移 == 4
quality_code  的偏移 == 8
```

| 概念 | 表示的内容 | 不表示什么 |
| --- | --- | --- |
| `sizeof(T)` | 一个完整 `T` 对象占用的 byte 跨度，包括必要填充 | 成员状态包含多少有效信息 |
| `alignof(T)` | `T` 作为完整对象时必须满足的地址要求 | `T` 的大小或处理器缓存块大小 |
| 成员偏移 | 成员起始地址相对完整对象起始地址的距离 | 不能只由前面成员大小简单相加得到 |

`sizeof` 与 `alignof` 都是运算符；对这里的类型形式使用它们，不会创建对象，也不会读取某个对象的成员状态。对于本章讨论的普通完整对象类型，`sizeof(T)` 包含让下一个连续 `T` 对象仍能满足对齐所需的尾部填充，因此对象跨度能够被其对齐值整除。

结构体大小大于成员大小之和，不表示填充是另一个隐藏成员。填充只服务于布局约束，不具有成员名称、独立类型或业务值。

## 对象表示、值表示与填充不是同一层概念

类型 `T` 的对象表示（object representation），是一个完整 `T` 对象占用的 `sizeof(T)` 个 `unsigned char` 对象组成的序列。当前 `sensor_sample` 的 12 bytes 整体构成它的对象表示，其中包括三个成员子对象占用的区域、三个内部填充 bytes 和三个尾部填充 bytes。

对象表示中参与表示 `T` 某个值的 bits 构成值表示（value representation）；其余 bits 称为填充位（padding bits）。某个基本类型自身就可能具有填充位；在当前 `sensor_sample` 示例中，结构体内部填充和尾部填充则是在成员子对象之间或之后出现的完整 byte 区域。二者相关，却不能把“类型内部不参与表示值的 bit”和“成员之间没有子对象占用的 byte”机械当成同一个布局层次。

填充区域不对应任何成员状态。因此，两个结构体对象即使每个成员值都相等，也不能仅据此假定完整对象表示中的每个 bit 都相同。正文中的结构体复制按照成员语义建立结果，也不要求复制结果的所有填充 bits 与源对象保持相同模式。

## 成员顺序能够改变填充数量

保持相同的三个成员类型，只调整声明顺序：

```cpp
struct compact_sample {
    int pressure_kpa;
    char status_code;
    char quality_code;
};
```

在同一目标假设下，`pressure_kpa` 位于偏移 `0～3`，两个 `char` 成员分别位于偏移 `4` 和 `5`。成员在偏移 `6` 处结束，为了让完整对象跨度仍满足四字节对齐，只需留下两个尾部填充 bytes，因此 `sizeof(compact_sample) == 8`。

这不是 C++ 对所有平台给出的固定结果，而是同一 ABI 规则下的重新推导。成员顺序还决定聚合初始化器的对应位置，改变顺序可能影响源码接口和 ABI；不应仅为减少几个 bytes 就随意重排已经公开的数据结构。只有对象数量、存储压力或访问性能形成真实约束时，才应在具体目标上测量并作出设计选择。

## 原始对象布局不是稳定数据格式

当结构体跨越已经编译的模块边界时，各方必须使用兼容 ABI。调整成员顺序、改变成员类型、切换目标 ABI 或采用不同布局选项，都可能改变成员偏移与完整对象大小；即使两个版本的 `sizeof` 恰好相同，也不能证明对应成员仍位于相同位置。

文件和网络协议还需要面对整数宽度、byte 顺序、版本演化等问题，不能把某次构建得到的结构体对象表示直接当作稳定格式。持久化与传输应定义明确的数据字段和编码规则，再由程序在这些字段与对象成员之间转换。

对象布局是语言约束、目标 ABI 与机器能力共同落地的结果。语言语义决定成员是什么，ABI 让编译产物对成员在哪里达成一致；二者不能互相替代。
