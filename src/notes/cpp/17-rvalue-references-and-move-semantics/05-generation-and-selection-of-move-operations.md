# 移动操作的生成与选择（Generation and Selection of Move Operations）

资源成员已经能正确转交责任时，包含它的对象未必需要再手写一遍交接逻辑。不过，判断一条带有 `std::move` 的语句会做什么，仍然要分清两个问题：类是否具有可用的移动操作，以及重载决议是否选择了它。

## 什么时候会隐式声明移动操作

如果类没有自行声明复制构造、复制赋值、移动构造、移动赋值和析构函数，编译器会隐式声明移动构造函数与移动赋值运算符。普通的业务构造函数不会阻止这两项声明。

自行声明上述任一特殊成员函数，都会阻止编译器再隐式声明移动操作；需要哪一项移动能力，就应当明确提供哪一项。这里判断的是“是否自行声明”，所以写成 `= default` 或 `= delete` 也会产生影响。手写一个析构函数，并不意味着编译器会替它配套推断资源交接方式。

声明存在还不代表一定可用。默认移动操作需要通过相应的成员操作完成工作；如果某个必要操作不可用，默认移动操作可能被定义为删除。移动构造与移动赋值分别判断，例如 `const int` 成员可以初始化，却不能在赋值中成为被修改的目标。

## 默认移动把成员分别交给相应操作

示例使用具有[移动构造](03-move-construction-and-resource-transfer.md#让源对象能够处于无责任状态)和[移动赋值](04-move-assignment-and-existing-resource-responsibility.md#结束旧责任再接收新责任)的 `registration`：它能转交登记责任，并让源对象进入空状态。下面的定义放在该类及其移动赋值定义之后，把轮胎编号与一项登记组合为一个检查对象：

```cpp
struct inspection {
    int tire_id;
    registration entry;

    inspection(int id, int& count) : tire_id{id}, entry{count} {}
};
```

这个类型满足隐式声明移动操作的条件。在已包含 `<utility>` 的源文件中，函数体可以使用：

```cpp
int count{0};
inspection source{1, count};
inspection target{std::move(source)};
```

默认移动构造按照成员声明顺序，用源对象中对应的成员初始化新成员。在这个类型中，两个来源成员都作为将亡值参与初始化：`int` 成员取得源编号的数值；`entry` 成员选择它自己的移动构造函数，转交登记并清空源成员。

因此两个对象的 `tire_id` 都为 `1`，但只有 `target.entry` 仍处于活动状态，活动计数仍为 `1`。默认移动并没有要求所有源成员都清零。默认移动赋值也逐成员进行，只是对已经存在的目标成员执行赋值，而非初始化。

组合对象的隐式复制操作则因登记成员不可复制而被删除。它自然获得了“可以转交、不能复制”的能力，不必在外层重新实现登记规则。

> 默认移动是逐成员选择操作，不是逐字节搬运，也不保证每个成员都调用移动函数。若某个类类型成员只能通过 `const` 左值引用复制，且没有更优的可选移动操作，默认移动也可能复制该成员。
>
> 对于直接承担登记责任的 `registration`，默认移动却不合适：裸指针成员只会取得源指针值，不会把源指针设为空，因而无法维持唯一的解除责任。责任已经被成员类型封装好，才是外层可以安全采用默认语义的依据。

## 显式要求默认实现

确实需要在类定义中明确写出默认移动能力时，可以在 `inspection` 中增加：

```cpp
inspection(inspection&&) = default;
inspection& operator=(inspection&&) = default;
```

`= default` 请求的仍然是成员式移动，不会绕过成员的访问限制或恢复已经删除的成员操作。自行声明了移动构造或移动赋值后，未自行声明的复制构造与复制赋值会被定义为删除；若类型还需要复制，就必须明确决定并提供对应的复制接口。

在 `inspection` 当前没有额外特殊成员声明的情况下，省去这两行就能得到需要的移动行为。显式默认化用于表达必要的接口选择，不需要成为每个类都照抄的清单。

## 构造函数的隐式声明规则对照

无实参创建对象、从同类型对象复制或移动，以及接收其他初始数据，适用的声明规则不同。下表以 `T` 表示类名，汇总几种常见构造接口：

| 构造接口（常见形式） | 隐式声明与删除规则 |
| --- | --- |
| 默认构造 `T()` | 类没有任何用户声明的构造函数时，隐式声明 |
| 复制构造 `T(const T&)` | 没有用户声明的复制构造函数时，隐式声明；若类声明了移动构造或移动赋值，这项隐式复制构造被定义为删除 |
| 移动构造 `T(T&&)` | 没有用户声明的移动构造，且没有用户声明的复制构造、复制赋值、移动赋值或析构函数时，隐式声明 |
| 普通带参构造 `T(int)` | 不会按数据成员自动生成；由类作者提供所需接口 |

这里的“用户声明”包括写出 `= default` 或 `= delete`，不要求手写函数体。在未额外声明特殊成员的 `inspection` 定义中，普通构造函数 `inspection(int, int&)` 会阻止编译器提供[隐式默认构造](../10-class-interfaces-and-encapsulation/04-constructors-and-member-initialization.md#默认构造函数何时由编译器提供)，却不阻止该类隐式声明复制或移动构造；它的复制操作不可用，是因为 `registration` 成员不能复制。

隐式声明只解决接口是否存在。成员操作不成立时，默认化的构造函数仍可能被定义为删除；调用处还要满足访问权限与重载选择规则。**判断构造调用时，既要看类声明了哪些构造函数，也要看初始化选中了哪一项，以及选中的函数能否合法调用。**

## 没有移动操作，也可能接收右值

下面的读数快照类型只有普通构造与自行声明的复制构造，没有移动构造：

```cpp
struct snapshot {
    int value;

    explicit snapshot(int measured) : value{measured} {}

    snapshot(const snapshot&) = default;
};
```

在包含 `<utility>` 的函数体语境中，下面的初始化仍然成立：

```cpp
snapshot source{240};
const snapshot copy{std::move(source)};
```

复制构造的 `const snapshot&` 可以绑定将亡值，因此这次初始化执行复制。源对象的数值仍为 `240`。接受右值输入，是引用绑定的能力；具有移动构造函数，则是类实际提供了哪一种特殊成员函数，二者不能等同。

即使类型同时提供常见的 `T(T&&)` 和 `T(const T&)`，`const T` 来源经 `std::move` 后仍不能绑定前者，因而可能选择复制；如果复制也不可用，初始化就会失败。

## 不存在与被删除的移动操作并不相同

> 当常见的移动构造与复制构造都能接受一个非 `const` 将亡值时，右值引用绑定使移动构造更优。这个选择规则与删除函数规则共同产生下面的区别：
>
> | 移动构造的情况 | 对当前初始化的影响 |
> | --- | --- |
> | 没有声明移动构造 | 没有这项候选；可用的 `const T&` 复制构造仍可能接收右值 |
> | 移动构造可用 | 对匹配的非 `const` 将亡值，优先于常见的 `const T&` 复制构造 |
> | 显式写成 `T(T&&) = delete` | 仍参与选择；如果选中它，调用报错，不自动改选复制 |
> | 默认化的移动构造因成员条件被定义为删除 | 在重载决议中被忽略；如果仍有可用的复制构造，可能改由复制接收 |
>
> 默认化后被定义为删除的移动赋值也会在重载决议中被忽略。这项规则只排除相应的移动候选，不会恢复已经被删除的复制操作。
