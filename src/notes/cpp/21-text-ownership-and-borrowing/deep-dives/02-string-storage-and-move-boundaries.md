# 字符串的存储选择与移动边界（String Storage and Move Boundaries）

`string` 拥有连续字符，但“拥有”不规定这些字符一定放在对象外部。这个实现空间解释了[文本借用的移动边界](../05-text-lifetimes-and-interface-boundaries.md)：目标取得文本值，并不总是意味着目标接管了字符原来的地址。

这里区分接口保证与存储机制。无论字符放在哪里，`string` 都负责自己的文本，`string_view` 都只借用字符；程序首先依据这些契约安排有效期，存储方案用于理解成本与地址行为的差别。

## 短文本可以直接放进拥有者对象

常见实现会在 `string` 对象内部预留一小块字符空间。文本适合这块空间时，可以直接使用它，省去单独分配和释放字符存储的开销。这种实现技术称为短字符串优化（Small String Optimization，SSO）。

以 libc++ 的一种实现为例，它准备了短文本与长文本两种表示：短表示直接包含字符数组，长表示保存通向外部字符存储的指针及数量等信息。下面只画拥有关系，不表示真实成员顺序或字节布局：

```text
内嵌存储：string 对象 [管理信息 | 字符空间]

外部存储：string 对象 [管理信息 | 指针] ──拥有──> 字符存储
```

两种表示服务于同一个 `string` 接口。字符较少时避免额外分配，超过内嵌空间的能力时仍能使用外部存储支持增长。给对象留下内嵌空间本身也有成本：每个 `string` 对象的表示需要容纳这种选择，即使某个对象实际采用外部存储。

SSO 是实现选择，不是 C++23 要求所有标准库采用的固定布局。内嵌空间大小、选择条件和表示方式都可能随标准库、平台及构建配置变化；仅凭文本“看起来很短”，不能在可移植代码中判定这次创建没有分配存储。

## 移动的成本取决于能转交什么

[移动构造](../../17-rvalue-references-and-move-semantics/03-move-construction-and-resource-transfer.md)允许类型利用源对象现有的资源建立目标，不要求每种类型都执行同一种“交换指针”动作。

对于采用上述两种存储方式的实现，可以推演出不同的机会与限制：

| 源字符的位置 | 移动到另一个 string 对象时的机制 |
| --- | --- |
| 源对象内部的字符空间 | 这块空间属于源对象自身，不能变成目标对象的成员；目标需要在自己的表示中保存字符值 |
| 源对象拥有的外部存储 | 实现可以把该存储的管理责任转交目标，从而避免逐个复制整段文本 |

因此，短字符串的移动可能仍包含字符复制。这不意味着移动机制失去了意义：内嵌空间大小有固定上限，复制这小段内容可以避免为了“只转交指针”而额外创建外部存储；较长文本则可能通过转交存储避免随文本长度增长的复制工作。

这里的机制不能扩大成接口没有给出的保证。普通 `string` 移动构造保证目标取得源原来的文本值，源保持有效但状态未指定；它不保证旧字符访问一定跟随目标。内嵌存储已经提供了直接原因：原来指向源对象内部的视图，不会因为字符值出现在目标中，就自动改为指向目标的内部空间。

> [!IMPORTANT]
> 文本值相同、字符位于同一地址、由同一个拥有者维持，是三个不同的判断。移动可以保留文本值并改变存储关系；读取移动后的目标时，从目标重新建立视图，才能把借用明确关联到当前结果。

## 对象大小不是整份文本的存储账单

`sizeof(string对象)` 给出对象本身占用的字节数，包括实现放在对象内部的管理信息、内嵌空间和填充。它不会沿着指针继续统计外部字符存储。

所以，同一实现下，一个短字符串对象与一个长字符串对象具有相同的 `sizeof`，不代表它们使用了相同数量的全部存储。`size()` 回答的是文本包含多少个 `char`，也不用于计算拥有者对象及其额外存储的总字节数。

> [!PRACTICE]
> 文本是否需要独立保存，应先由接口职责和生命周期决定。SSO 可以降低某些小字符串的成本，却不能消除复制的语义，也不能保证每次复制都无需分配。若性能确实受到影响，应在目标标准库和真实文本分布下测量，再决定是否减少拥有的副本或改变借用安排。
