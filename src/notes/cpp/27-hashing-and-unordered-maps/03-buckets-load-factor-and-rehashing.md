# 桶、负载因子与重哈希（Buckets, Load Factor, and Rehashing）

批量登记传感器时，无序映射不仅要增加记录，还可能需要增加桶，把已有记录重新分组。预先知道大致规模，就可以提前安排这部分工作；判断该准备多少空间，需要先分清元素数量、桶数量和桶内的拥挤程度。

## 桶数与元素数是两项状态

`size()` 统计已经保存的键值关联，`bucket_count()` 统计当前桶数，两者没有一一对应关系。桶可以为空，也可以容纳多个元素；准备更多桶不会自动创建传感器记录。

需要观察分布时，可以使用下面的接口。这里的桶编号只是容器内部某个桶的索引，与业务编号、哈希值本身都不是同一概念。

| 接口 | 含义与前提 |
| --- | --- |
| `bucket_count()` | 返回当前桶数；默认构造的空容器有多少桶，不应写死 |
| `bucket(key)` | 返回该键应当查找的桶编号；要求当前桶数大于零，键本身可以不存在 |
| `bucket_size(index)` | 返回指定桶中的元素数；要求 `index < bucket_count()` |

这些接口都返回容器的无符号计数类型 `size_type`。`bucket(key)` 的结果落在 `[0, bucket_count())`，可以交给 `bucket_size` 查询该桶的记录数，但桶中有记录不等于目标键存在。判断目标是否存在仍使用 `find` 或 `contains`。

例如，若 `bucket(20)` 返回 `3`，含义是应在编号为 `3` 的桶中查找键 `20`，并不表示第三条记录的键就是 `20`。桶重新组织后，同一个键的桶编号也可能改变。

## 哈希值不变，所属的桶仍可能改变

**重哈希（rehashing）是按照新的桶组织重新安排已有元素。** 它不增删已有键值关联，也不要求同一个键得到不同的哈希值；改变的是元素所属的桶和遍历关系。

桶的选择关系变化后，已有记录也需要与新的查找路径对应起来。因此，为更多记录准备桶，可能涉及整个容器的重新组织。哈希值如何对应到桶、增加桶为什么需要重新分组，可以沿着附章的[四个桶变为八个桶的过程](./deep-dives/01-hash-values-collisions-and-bucket-organization.md#增加桶时已有记录也需要重新分组)推演。

## 负载因子描述平均拥挤程度

**负载因子（load factor）是每个桶平均容纳的元素数量。** `load_factor()` 返回 `float`；在桶数大于零时，这个平均值就是元素数除以桶数，按浮点数表示。

例如，八个元素分布在四个桶中，负载因子为 `2`。这不意味着每个桶都恰好有两个元素；某个桶可能为空，另一个桶也可能装下全部八个元素。

`max_load_factor()` 返回容器当前采用的最大负载因子，是控制平均拥挤程度的正数。插入使元素数量增加时，容器会按需要增加桶，并通过重哈希重新安排已有元素所属的桶。

带参数的 `max_load_factor(value)` 用来请求调整这项阈值，参数必须为正。例如，`readings.max_load_factor(0.5F);` 请求让平均负载保持在更低水平。C++23 将这个参数规定为调整提示，实际采用的阈值应通过不带参数的 `max_load_factor()` 读取，不应直接把传入值当成保证。

调整阈值也不等于立即把已有元素重新分桶。如果需要按照调整后的阈值准备桶，应再使用 `reserve` 或 `rehash`。阈值越低，容纳相同数量的元素通常需要越多桶；它带来的是空间与查询工作量的取舍，没有适合所有数据的固定数值。

> [!IMPORTANT]
> 负载因子描述整体平均值，不限制单个桶最多容纳多少元素。最大负载因子控制容器何时需要更多桶，不能保证每个桶都均匀，也不能保证一次查找只比较一个键。

## 按预计元素总数准备桶

`reserve(count)` 按预计的**元素总数**准备桶，`rehash(count)` 则直接提出**桶数下限**。两者返回 `void`，都不会增删已有键值关联。

| 操作 | 成功返回后需要满足的条件 |
| --- | --- |
| `reserve(count)` | 按当前最大负载因子，为总计 `count` 个元素准备足够的桶，同时容纳已有元素 |
| `rehash(count)` | 桶数至少为 `count`，并且足以使已有元素满足当前最大负载因子 |

`reserve` 会把元素数量换算成所需桶数：用 `count` 除以当前 `max_load_factor()`，再向上取整，随后执行相应的 `rehash`。这里的向上取整是数学上的数量换算，不要求调用者自己实现它。

若当前采用的最大负载因子为 `0.5`，准备容纳八个元素就至少需要十六个桶。实现可以选择更多桶，因此 `reserve(8)` 不保证恰好八个或十六个桶，`rehash(32)` 也不保证恰好三十二个桶。传入小于当前规模的请求，同样不能强制容器缩到那个数。

下面先请求负载阈值，再按预计总数预留，随后插入三条记录。最后直接提出桶数下限，观察元素是否保留。

```cpp
#include <iostream>
#include <unordered_map>

int main() {
    std::unordered_map<int, int> readings{};
    readings.max_load_factor(0.5F);
    readings.reserve(8);
    std::cout << readings.size() << '\n';

    readings.try_emplace(10, 240);
    readings.try_emplace(20, 245);
    readings.try_emplace(30, 250);
    std::cout << readings.size() << ' ' << readings.at(20) << '\n';

    readings.rehash(32);
    std::cout << (readings.bucket_count() >= 32) << '\n';
    std::cout << readings.size() << ' ' << readings.at(20) << '\n';
}
```

输出依次为 `0`、`3 245`、`1` 和 `3 245`。预留之后容器仍为空；重哈希之后记录数量和压力值仍在。程序只检查桶数下限，不依赖具体桶数或遍历顺序。

这里的 `8` 是计划保存的总数。如果已经有六条记录，预计还会增加四个不同键，应按总计十条准备，而不是调用 `reserve(4)`。重复键不会增加元素数量，估算依据是最终要保留的不同键数量。

> [!WARNING]
> 重哈希会使已有迭代器失效，即使键值记录仍然存在；指向元素的指针和引用则保持有效。执行 `reserve`、`rehash` 后，应重新取得需要使用的迭代器，也不能继续把旧桶编号当成该键的当前桶编号。

## 预留解决重组频率，不保证没有分配

`vector` 的[预留容量](../11-sequences-and-data-access/04-sequence-storage-and-reference-validity.md#已知数量时预留容量)为连续元素存储安排空间。无序映射的 `reserve` 按元素总数安排桶，不能据此推导出后续插入都不再申请内存：新元素自身仍可能需要分配，其映射值的构造也可能另有分配。

在最大负载因子不再改变、桶也没有被主动重新调整的条件下，合理预留可以避免计划规模内的插入反复触发重哈希。重哈希本身需要处理已有记录，平均复杂度与元素数成正比，最坏可能达到平方级；它并不是一项只修改计数器的操作。

更多桶也不能修复哈希分布本身的问题。如果所有键都得到相同哈希值，它们[增加桶后仍然聚集在同一个桶](./02-custom-hashes-and-key-equivalence.md#碰撞保留记录但可能增加查找成本)。此时整体负载因子可以很低，拥挤的那个桶却没有变短。

> [!PRACTICE]
> 批量导入且能估计最终记录数时，可以在导入前预留；若需要调整负载阈值，先调整，再按容器实际采用的阈值预留。查询仍然偏慢时，要同时检查键的哈希分布与数据规模，而不是只继续增加桶数。
