# 操作次数与空间范围（Operation Counts and Space Scope）

“线性”“平均常数”是对成本随输入规模增长的约束，不是某次运行所花的毫秒。理解标准库契约，先说明规模、计数对象和统计范围。

## 渐近界限描述增长方式

时间复杂度（Time Complexity）分析基本操作次数怎样随规模增长；空间复杂度（Space Complexity）分析所需存储怎样增长。`O(f(n))` 描述在足够大的规模下，成本可以由常数倍的 f(n) 从上方约束。

n 可以是元素个数，也可以是字符数。遍历 n 个整数与遍历 n 个大型对象，都可能只执行 n 次迭代，却不因此具有相同耗时。

| 当前操作 | 常见计数对象 |
| --- | --- |
| 查找、排序 | 比较次数，以及迭代器推进次数 |
| 哈希映射查询 | 哈希计算、桶内比较；文本键还涉及字符处理 |
| vector 增长 | 新元素构造、已有元素迁移和分配 |
| 视图遍历 | 基础元素检查、回调调用和结果读取 |

对长度为 k 的文本键计算哈希可能处理 k 个字符；“表查询平均常数”不证明整次文本处理独立于 k。

## 最坏、平均与摊还是不同承诺

最坏情况（Worst Case）对该规模下允许输入取最大成本。平均情况（Average Case）依据输入或随机过程的假设作平均。摊还分析（Amortized Analysis）将一串操作的总成本分摊到每项，不需要假定每个输入随机。

vector 尾部添加通常有摊还常数的元素操作成本，但触发再分配的单次添加需要迁移已有元素。对一串增长操作的保证，不承诺每次调用都有固定延迟，也不规定容量必须翻倍。

哈希映射的平均查询与碰撞严重时的最坏线性情况，是另一种区别；不能把平均一律改称摊还。

> [!IMPORTANT]
> 每次引用复杂度，都同时找规模、基本操作、情况类别和前置条件。比较次数、分配次数与实际耗时可以相关，但不能直接互相代换。

## 空间必须说明算哪些存储

输入存储、输出存储和额外工作空间分别统计。筛选 n 个值得到 m 个独立结果，结果容器本身需要随 m 增长的存储；只记录算法内部临时变量可能得到常数额外空间，但不能说整个结果免费。

vector 还要区分 size 与 capacity。容量提供已分配存储，size 决定实际元素对象数；粗略存储估计包含容量乘以元素大小，还可能有分配器和对象管理开销。

视图不生成整份中间结果，通常能降低额外存储，但源数据、拥有视图中的容器及回调状态仍然存在。

> [!PRACTICE]
> 用复杂度排除规模增长明显不合适的方案，再依据相同语义和真实输入测量时间、分配与峰值存储。小数据中的常数、局部性和对象成本可以改变实际排序。
