# 扩展接口与工程取舍（Extension Interfaces and Engineering Choices）

压力报告程序已经有完整的输入、值、处理和输出责任。扩展时围绕出现的新问题选择设施，不把更复杂的语言能力当作必然升级。

## 先判断哪项契约发生变化

| 新需求 | 首先调整的关系 |
| --- | --- |
| 一次处理很多数据，只需要一个均值 | 明确流式处理与部分失败策略，减少整份结果存储 |
| 重复使用筛选后的记录 | 比较延迟视图与拥有型快照的成本和寿命 |
| 替换几种数据来源 | 判断共同流接口、模板适配或运行时抽象是否满足职责 |
| 多个组件保留同一份结果 | 区分共享不可变结果与各自可修改副本 |
| 多个独立文件同时处理 | 明确任务拥有输入、结果、取消及最终等待责任 |
| 外部程序调用服务 | 设计编码、版本、所有权和错误边界，而非暴露内部布局 |

当前 pressure 是一个小值，复制成本低且有独立身份。为了避免它的普通复制而改用共享指针，会增加责任管理和间接访问，不一定提高性能。

## 成本结论跟随任务范围

解析成本随字符总数增长，保存全部记录的空间随记录数增长，临时行缓冲随最长行增长。最终报告很短，不代表整份程序使用常数空间。

当前程序选择先保存一份完整的、已经验证的记录集合，再让只读计算接口取得它。这样，输入失败定位与均值计算可以分别检查：计算不必依赖流状态，成功结果也不再借用临时行或输入资源。代价是保存 N 条记录需要 O(N) 空间；仅求一次均值并不要求必须采用这个方案。

若任务确实只求一次均值，可以逐行验证后累积总和与数量；全部输入成功且数量非零时，才生成最终报告。累积状态的空间相对于记录数为 O(1)，行缓冲仍随最长行增长。后来遇到坏行时，舍弃此前累积状态，不把部分均值当作完整结果。

两种方案都可以把输出推迟到全部输入验证之后。全量保存本身不提供输出事务保证，流式计算也不必提前产生外部副作用。若新增需求是重复分析或保留独立快照，保存记录的收益又会改变；选择应跟随实际任务。

并发也需要任务独立性和足够工作量。每一行都创建一个线程通常使调度和责任成本支配计算；任务分组与执行资源应依据真实负载设计。

> [!PRACTICE]
> 先写清新的可观察行为、失败状态与生命周期，再选择类型、模板、范围或同步设施。保持一个调用方能推演的接口，比在同一程序中展示尽可能多的关键字更重要。

## 稳定知识模型支持新的具体工具

表达式与类型解释操作选择；对象模型解释身份和有效期；资源模型解释责任结束；结果类型解释失败；名称与程序组织解释接口可见性；泛型、多态、范围和并发分别扩展这些关系。

进一步的算法设计、完整 Unicode、平台 I/O、数值分析等专业能力，按对应问题形成独立专题。C++ 设施提供组合基础，并不自动替代这些领域自己的正确性证明。
