# C++ 代码规范

## 适用范围

本规范约束 `src/notes/cpp/` 中的 C++ 代码示例，以及随笔记建立的练习、验证程序和示例项目。语言基线为 C++23。

代码以现代 C++ 标准库（C++ Standard Library）为基础，并继承 STL 将数据结构、迭代方式与算法解耦后重新组合的设计思想。这里的“标准库优先”不是要求每段代码都使用复杂模板或算法，而是当标准库已经提供语义合适、边界清晰的抽象时，不再自行维护一份脆弱的替代实现。

**标准库优先、值语义优先、RAII 优先、组合优先，最终以清晰而准确地表达意图为准。**

笔记正文仍受知识依赖约束。某项现代设施尚未正式引入时，可以使用读者已经掌握的基础形式建立当前概念，但不能因此把基础形式暗示为长期首选。展示 C API、平台接口、CUDA 或遗留代码时，可以保留边界所要求的类型和写法；边界以内重新回到本规范。

## 判断顺序

出现多种合法写法时，依次考虑：

1. 是否具有正确的语言语义、对象生命周期和所有权关系；
2. 是否直接表达当前业务意图；
3. 是否已有合适的标准库抽象；
4. 是否比替代写法更容易阅读、验证和维护；
5. 是否存在经过测量的性能或平台约束。

风格不能为错误语义辩护，性能猜测也不能自动推翻更清晰的实现。确实偏离默认规则时，应当能够说明具体约束，而不是只以“可能更快”作为理由。

## 标准库作为基础

### 类型与资源

- 普通对象和值语义是默认选择；资源交由具有明确生命周期的对象管理。
- 固定长度序列优先考虑 `std::array`，动态连续序列默认从 `std::vector` 开始选择。
- 文本默认使用 `std::string`；只读且不拥有文本的接口可以在生命周期明确时使用 `std::string_view`。
- 不拥有的连续对象序列可以在生命周期明确时使用 `std::span`。
- “可能没有值”使用 `std::optional` 等类型表达，不使用含义隐蔽的特殊整数。
- 独占动态所有权默认使用 `std::unique_ptr`；只有对象确实具有共同生命周期时才使用 `std::shared_ptr`。
- 裸指针和引用主要表达非拥有关系。应用代码不直接用成对的 `new` 与 `delete` 管理资源。

这些都是语义起点，不是只凭类型名称作出的机械选择。例如，需要频繁随机访问和连续存储时，`std::vector` 通常比链式容器更自然；只有访问模式和约束确实匹配时，才选择其他容器。

### 算法、范围与循环

- 标准算法或 ranges 能直接说出“查找、变换、排序、计数”等意图时，优先使用相应设施。
- 普通循环在状态变化、提前退出或控制流更清晰时可以直接使用，不为了形式上的“现代”强行改写。
- 迭代对象时优先面向范围；只有下标本身具有业务含义时，才把下标作为核心接口。
- 不依赖容器的内部实现细节，不保存可能因容器修改而失效的迭代器、指针或引用。

**STL 风格的重点是以稳定接口组合数据与操作，不是把所有循环改写成一行算法。**

## 命名与命名空间

- 自定义类型、函数、变量、命名空间和枚举值统一使用 `snake_case`。
- 名称表达业务含义，不重复类型，不使用无意义缩写，也不借名称隐藏单位。
- 常量继续使用语义化的 `snake_case`，不因具有 `const` 或 `constexpr` 限定而改成全大写。
- 模板参数只有在范围很小且惯例明确时使用 `T` 等单字母名称，否则使用能够说明约束或角色的名称。
- 宏只用于确实需要预处理器的场景；无法避免时使用能够降低冲突风险的全大写前缀名称。
- 标准库名称显式保留 `std::`。头文件和命名空间作用域中不使用 `using namespace std;`。
- 不声明以下划线开头或包含双下划线的自定义名称，也不向 `std` 命名空间随意添加声明。

## 初始化、类型与转换

- 对象在声明位置完成初始化，并尽量靠近第一次使用的位置创建。
- 简单对象默认使用花括号初始化，以拒绝明显的窄化；当复制初始化、类型推导或特定构造形式更准确地表达语义时，不机械要求花括号。
- 不打算在初始化后改变的对象使用 `const`；其值属于编译期语义时再使用 `constexpr`。
- `auto` 用于避免重复显而易见或冗长的类型，不用于隐藏数值类别、所有权或关键生命周期关系。
- 空指针使用 `nullptr`，具有独立取值集合的状态优先使用作用域枚举。
- 必须转换类型时使用能够表达意图的 C++ 具名转换，不使用 C 风格强制转换。
- 不混合有符号与无符号算术，不让隐式窄化替代业务上应当明确的范围判断。

## 函数接口与所有权

- 复制成本低且本来就需要独立值的输入按值传递。
- 只读取且不应复制的对象通过 `const T&` 传递。
- 必须修改调用方对象时使用 `T&`，并让函数名称能够反映修改行为。
- “可以没有目标”的非拥有参数使用 `T*`；不能为空的非拥有关系优先使用引用。
- 输出默认通过返回值表达，不把非 `const` 引用或指针惯性地当作输出参数。
- 不返回指向局部对象的指针、引用或视图。
- 共享所有权必须是领域语义，而不是为了回避生命周期设计而使用 `std::shared_ptr`。

接口应让调用者从类型和名称中看出对象是否会被修改、是否可以为空，以及谁负责维持生命周期。

## 源文件与依赖

- 每个源文件直接包含自己实际使用的声明，不依赖其他头文件偶然产生的传递包含。
- 标准库头文件使用尖括号，自有头文件使用双引号。
- 头文件应当能够独立包含，并使用可靠的 include guard 或 `#pragma once`。
- 头文件不引入广域 `using` 指令，不暴露完成接口并不需要的实现依赖。
- 优先缩小依赖边界；不能以牺牲类型完整性和可读性为代价追求最少字符。

## 格式

仓库根目录的 `.clang-format` 是 C++ 排版的可执行事实源。正文只保留影响阅读和语义的约束：

- 使用四个空格缩进，不使用制表符；
- 每行默认不超过 100 个字符；
- 左花括号与控制语句或函数声明保持同一行；
- 指针与引用符号靠近类型，写作 `int* pointer` 和 `const int& value`；
- 条件和循环即使只有一条语句也保留花括号；
- 一条声明语句只声明一个对象；
- 复杂表达式用括号和具有含义的中间名称表达结构，不依赖读者背诵优先级表。

格式化工具只统一排版，不能判断容器选择、生命周期、所有权或接口语义。代码在格式化后仍然难以理解时，应当调整结构，而不是继续增加格式规则。

## 示例审阅

完成或修改代码示例后，应当检查：

- 是否在当前知识依赖允许的范围内使用了最合适的标准库设施；
- 每个对象的所有权、有效期和可修改性是否清楚；
- 容器是否依据数据规模和访问方式选择；
- 算法、ranges 与普通循环之间的选择是否让意图更直接；
- 是否存在不必要的手工资源管理、隐式窄化或复杂副作用；
- 是否显式保留 `std::` 并遵循统一命名；
- 将示例放入其注明的语境并补齐必要程序外壳后，是否能够通过格式化、编译和相应警告检查。
