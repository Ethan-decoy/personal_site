# Markdown 提示块

本页统一约定提示块的成框依据、类型取舍与写法。内容范围与掌握要求分别遵循 [C++ 写作规范](./writing-style.md#掌握要求)或 [Python 写作规范](../../python/_guidelines/writing-style.md#掌握要求)。

## 内容与选型

**先确定要独立取用的结论，再选择类型。**正文默认承担当前例子的展开与状态推演；需要反复回顾的关系、可复用方法、容易遗漏的边界或需单独查阅的补充，才提炼为提示块。框中应能找到结论及其必要条件，不依赖读者记住某个例子的临时状态。

掌握要求与类型分别判断。需要熟记不等于都用蓝框；同一知识可以既需熟记又用于排查或纠错。选型依据是框中实际提炼的结论及其用途：

| 类型 | 何时选用 | 内容应支持的判断 |
| --- | --- | --- |
| `[!IMPORTANT]` | 提炼需要直接调用的通用模型或核心关系 | 哪些对象在什么条件下有什么关系，如何据此解释或推演同类情形；只有术语、口号或本例结果不足以成立 |
| `[!TIP]` | 提供核实状态、辨认结果、定位问题或完成操作的方法 | 检查什么、怎样检查，以及查明的情况如何影响判断或下一项动作；只说“需要注意”不构成方法 |
| `[!PRACTICE]` | 建议怎样组织或编写代码、设计接口或安排工作流程 | 采用该做法的条件与理由；有其他可行方式时，交代会影响选择的收益、代价或局限，不把建议写成语言保证 |
| `[!WARNING]` | 纠正具体的错误预期或用法 | 哪项假设会在什么条件下失效，产生什么后果；不能只因出现异常就归入此类 |
| `[!NOTE]` | 单独提供与主线有关的背景、来由或旁支补充 | 补充事实及其与当前问题的联系；不以补充说明代替主线当前必需的解释与条件 |
| `[!CAUTION]` | 当前要执行的操作存在实际损失风险 | 哪项操作可能损坏数据、文件、环境或外部状态，以及操作前应满足什么保护条件；普通运行失败不自动构成操作风险 |

背景本身是篇目主题时，应作为正文展开；`NOTE` 只承担其中需要单独定位的补充，不作为其他内容的兜底类别。

## 相邻类型的取舍

- **模型与方法：**解释可复用关系本身，用 `IMPORTANT`；说明怎样查明当前状态、辨认原因或完成操作，用 `TIP`。规则含有条件，不意味着它就是排查方法。
- **模型与易错边界：**核心关系的适用条件应随关系一起保留。需要额外纠正某种具体误判时，才围绕该误判及后果组织 `WARNING`；规则涉及失败，不意味着核心关系必须移出蓝框。
- **方法与工程建议：**核对已有事实或执行一项操作的方法，用 `TIP`；怎样组织代码或选择实现方式的建议，用 `PRACTICE`。后者即使列出选择条件，仍须看它是否在论证代码或流程的安排。
- **易错与操作风险：**误读规则导致的错误结果，用 `WARNING`；当前操作可能造成需提前防护的实际损失，用 `CAUTION`。说明一个危险行为的规律，与即将执行有风险的操作，判断用途不同。

同一段可以兼有多种作用。比较时看哪项结论需要被独立取用，以及各候选类型要求的信息是否实际具备。关联条件、解释和例子可以留在一框；两个结论确需分别定位时再拆分，保留各自条件。不同组织都符合这些边界时，可以有不同选型，不为凑类型或证明标签而补造内容。

## 对照例子

以下用 Python 简单名称赋值比较内容用途，不规定每篇采用哪些类型：

| 提炼的内容 | 选择及理由 |
| --- | --- |
| 赋值先求右侧的值，再让名称绑定所得对象；读取取得当前绑定的对象 | `IMPORTANT`：建立解释同类代码的通用关系 |
| 某一行输出了 `Hello, Python!` | 普通正文：当前例子的具体结果，尚无独立的通用结论 |
| 已有 `message` 绑定时执行 `message = 1 / 0`，旧绑定从未被清除，也没有被替换后再恢复 | `WARNING`：纠正“赋值开始就会清掉旧绑定”的预期，交代本例的失败条件与后果 |
| 脚本与交互会话的读取结果不同，核对执行历史与当前绑定 | `TIP`：提供查明差异原因的核对方法 |

## 写作与审阅

构思与复核均检查以下内容，判断留在作者工作中，不写进正文作为框体选型说明：

1. 从正文中指出拟提炼的结论、方法或补充，以及读者在哪类情形下会取用它；据此判断是否需要成框。
2. 对含有多种职责的内容，比较最接近的候选类型，核对各自要求的信息。说明“现有类型也能容纳它”不等于完成了选型比较。
3. 核对标题与正文是否指向同一项用途，结论的对象范围、条件、判断依据或后果是否完整。类型名本身不证明这些信息已经存在。
4. 从全文检查值得突出却遗漏的关系、方法与边界；同时检查已有框是否重复正文或彼此重复而没有新增用途。

核心关系应在建立处就地突出，文末回顾不代替首次标识。数量、篇幅与类型组合按内容需要选择，不设配额；同一结论的必要解释与就地提炼可以配合使用。

## 标题与写法

- 使用 `> [!TYPE] 可选标题`，块内使用普通 Markdown，每行（含空行）保留 `>`。
- `IMPORTANT` 应有概括对象、问题或关系的标题；其他类型按定位需要填写标题，不重复类型名称。
- 标题使用普通文本，不额外加粗或使用行内代码。蓝框已表明核心关系的掌握要求，标题与正文直接写知识，不另加“需要熟记”“重点记忆”等标签。
- 提示块可包含关联解释、例子、列表、表格、代码与公式，拆分以是否需要独立定位判断。

```markdown
> [!IMPORTANT] 静态链接与动态链接怎样提供实现
> **静态链接把所需实现并入输出产物；动态链接让相应实现保留在独立动态库中，启动或运行时仍需加载它。**
```

`PRACTICE` 是本站扩展。视觉约定见[设计规范](../../../../docs/DESIGN.md#24-markdown-文档排版)。
