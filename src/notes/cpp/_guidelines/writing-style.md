# C++ 主线写作规范

## 适用范围与约定分工

本规范约束 `src/notes/cpp/` 下的主线正文、章节索引、附章与综合篇，语言基准为 C++23。速查面向即时查用，使用独立的[速查写作规范](./quick-reference-writing-style.md)。

本规范负责知识建立、阅读负担、示例选择、掌握要求与正文表达。代码的命名、格式、接口倾向和标准库使用遵循 [C++ 代码规范](./coding-style.md)；提示块的语法、类型职责与标题遵循 [Markdown 提示块](./markdown-callouts.md)。规划新章、调整分篇或审阅全书覆盖时，另按[全书结构](./book-structure.md)核对范围、依赖与归属。

本文中，“应”“必须”“不得”“不能”表示要求；“默认”“优先”表示在没有更合适的具体理由时采用的选择；“可以”表示可选做法。要求用于判断内容质量，示例与建议用于帮助选择写法，不构成固定栏目、讲述步骤或篇幅配额。

## 读者与质量目标

C++ 笔记兼顾顺序理解与长期查阅。正文建立直觉完整、依赖闭合的知识主线，附章承载更深入的机制与精细规则。笔记不记录学习过程，也不承担练习、自测或学习进度跟踪职责。

默认的顺序阅读者已经读过前置内容，但缺少编程经验。介绍过一个概念，不等于读者已经熟练识别它的各种写法、追踪多组对象关系或补齐省略的步骤。解释应从前文实际建立的能力出发；随着同一关系被反复使用，再逐步缩减支撑。

> **窄入口，深模型；机制可以下钻，分类不横向蔓延。**

每篇正文应解决一个明确问题，在当前知识边界内建立最小准确模型。一个关键概念在当前层次建立完成，应使读者能够：

- 解释涉及的对象、操作与结果，并区分当前容易混淆的概念。
- 依据明确的条件和关系，推演相似代码的行为。
- 识别当前范围内的失败边界，说明哪项条件失效以及后果。
- 在涉及使用或工程选择时，说明当前操作或接口为何适用，以及已有证据足以支持什么判断。

只给出术语或类比，尚不足以建立这些能力。早期模型可以限定范围，但应保持准确；后续内容可以扩充范围、补足机制或细化边界，不应要求读者推翻先前赖以判断的错误关系。

阅读效率以掌握同一核心概念所需的总负担衡量。除必要难度，还应检查辨认符号、回忆前置、重建语境、追踪状态和筛选重点的成本。删减文字应保留必要条件和推理支撑；减少字数若把这些任务转交给读者，就没有降低理解成本。

## 主题边界与知识依赖

- 新内容不得依赖尚未建立的语义才能被正确理解。首次建立概念，应选能直接显现核心关系的情形，并说明当前范围。
- 理解当前行为、正确性、失败边界和必要工程判断所需的语义，应在使用前建立。只解释内部如何实现的机制可以后置。
- 高层抽象可以先于实现机制使用，但必须先给出足以判断当前行为的准确契约。
- 深入程度由当前问题的真实语义依赖决定。分类与扩展规则按实际判断需要引入；不追求首次出现时穷尽规则，也不因内容困难而省略必需条件。
- 篇章应按要解决的问题组织。名称、符号或底层表示相近，不能成为同时展开不同问题的理由。

## 内容归属

| 位置 | 应承担的职责 |
| --- | --- |
| 章节索引 | 说明本章解决的问题、关键关系与查阅入口；需要时补充导读，指出附章的阅读前提 |
| 主线 | 建立能够正确阅读、预测和使用当前概念的语义模型，保留影响当前正确性、安全边界与工程判断的条件 |
| 附章 | 在具备必要前置的基础上，深入标准规则、对象模型、实现机制、平台差异与极端边界 |
| 综合篇 | 用多个已建立概念解决工程问题，说明设计取舍，不另起未经铺垫的知识主线 |

内容归属以所需语义和当前用途判断。附章可以放在相关主线之后，也可以就地补齐必要使用契约；不能用附章链接代替主线当前必需的解释。索引已有标题足以导航时，可以保持简洁，不要求另写导读。

同一结论可以在首次建立处集中解释，后续根据推理或查阅需要适量回顾。回顾应恢复当前真正用到的关系，不重复整段前文。

## 讲解组织与查阅

### 问题、条件与因果关系

开头应让读者看出当前讨论的对象与问题，以及为什么需要讨论它。可以先给结论，也可以从例子、现象或矛盾引出；选择取决于理解效果，不要求固定开篇形式。

段落应围绕清楚的关系展开，使抽象结论能落回具体对象、操作与结果。条件怎样影响结果、推理依赖哪些中间关系，应在正文中可见；连续术语或多层判断使论述难以跟随时，应拆分、补充对应说明或使用例子。

引入新规则或方法，应说明当前尚未解决的问题及其适用条件；得到结果后，应说明结果解决了什么，以及据此能够作出什么判断。这里交代的是程序行为与概念关系，正文不以作者准备如何讲解、如何安排文章的构思说明代替内容。

### 前置联系与推演过程

- 复用前置知识时，应就地恢复当前判断所需的最短联系，写出实际依赖的结论。链接、“前面介绍过”或“后面会讲”不能代替必要解释。
- 跨段落推演时，应明确仍在追踪哪个对象、值或调用。转换表示或例子时，应说明相关对象、条件和结果如何对应。
- 进入子问题时，应让读者知道当前缺口；返回时，应恢复原目标与中间结果的用途。不要求每段重复目标。
- 需同时保留多个中间关系，或结果不易记住时，应通过名称、局部表格或图示把已知与未知留在可见位置。
- 应让核心关系先形成可使用的判断，再按需展开背景与机制；避免读者尚未得到当前结论，就必须在多个未完成问题之间往返。

这些要求用于控制理解负担，不规定术语数、代码行数或解释步骤。熟悉关系不必从头重讲，必要的准确条件也不能为降低表面难度而删去。

### 单篇查阅

小节标题应帮助定位对象、问题或结论。适用条件应与对应结论保持容易识别的联系，可以就近说明，也可以明确回指或链接。

单篇入口应通过适量回顾、前提说明或链接帮助定位必要前置，不要求重述整条知识链。顺读时应能得到完整因果解释；只扫标题、关键段落、表格与提示块时，也应能找到主结论、适用条件和相关边界。

## 示例的选择与论证

示例应服务当前模型与判断能力，数量以完成这一用途为限。情境是否恰当、关系是否贴合、语言语义是否准确和代码形式是否合规，应分别判断。

### 情境与对象角色

- 选择与审阅例子，应判断它能否直接显现当前概念所需的关系，并考虑有无更合适的替代情形。同样准确时，优先选择用途自然、背景负担更小的例子；简单数值与对象关系足以说明时，可以直接使用。
- 情境中的数据、对象关系和操作应自然合理。若例子依靠领域含义成立，应就近说明相关对象、成员或数值代表什么，以及操作要完成什么；说明深度以理解当前关系所需为限，不让读者仅凭英文标识符猜测含义。
- 与当前判断无关的专业知识、业务规则、单位换算或计量约定，不应成为理解门槛。名称中的必要单位与角色仍须清楚。
- 例子的操作应有与所述情境相符的用途。为展示机制而采用容易被误认为工程首选的写法时，应说明演示目的，并在已有知识范围内交代实际选择的依据。
- 新例子应让已建立的关系用于判断新的情形；切换情境或表示时，应说明与原问题的对应，保留跟进推理所需的联系。

### 代码语境与实际结果

- 示例只依赖已经建立的语义，不引入尚未建立且非当前结论必需的语言设施或标准库工具。确实不可替代时，应先建立足以理解示例的最小准确契约。
- 新代码形式应说明当前用到的组成、名称角色、合法放置位置与执行结果。程序外壳和辅助代码以当前问题所需为限，不顺带引入无关的库、背景或技巧。
- 代码块应是完整程序，或注明嵌入语境的 C++ 片段。片段之间接续、替换还是彼此独立，应足以辨认，避免按正文顺序使用时产生重定义或上下文缺失。
- 正文、代码注释、表格与图示中的类型、值类别、对象身份、状态、生命周期、求值过程和结果，应相互一致。代码按其注明语境核对，格式与验证要求遵循 [C++ 代码规范](./coding-style.md)。

### 对照、错误与结论

- 对照示例应实际显现要解释的区别，优先只改变影响当前结论的条件。应说明比较的对象或行为及各自结果；结果相同时，也要说清它支持什么判断。
- 展示错误代码时，应指出失败位置与原因；展示错误直觉时，应选能暴露后果的输入或条件，并直接解释结果。示例用于论证，不留给读者作答。
- 从示例得到的结论，应保留其对象范围与适用条件。具体输入、地址或实现下的结果，不应被直接概括成无条件规律。

## 掌握要求

作者应按当前判断的实际需要，区分需要熟记、理解重建与使用时查阅的内容，并在对应讲解中让读者看出要求。

| 掌握方式 | 选择依据 | 正文应交代的内容 |
| --- | --- | --- |
| 熟记并能直接调用 | 反复支撑阅读、判断或使用的概念关系、通用规则与操作模式；临场重建容易打断判断或遗漏条件 | 提炼可复用的关系、适用条件与判断用途，不把例子的每个具体结果变成记忆对象 |
| 理解依据与必要时重建 | 解释结论或展示如何由已知关系得到结果的推理、计算与过程 | 写清中间关系，使读者能够说明依据或重建判断；长篇推导和整段程序不要求逐句复述 |
| 使用时查阅并核对 | 随实现或任务变化、需要逐次确认的数据与规格，以及当前只需识别触发条件的细则 | 说明何时查、核对什么及可靠入口，在依赖这些条件的操作之前完成核对 |

同一知识可以同时需要熟记关系、理解依据和查阅精确细节。是否需要直接记起，应结合使用频率、重建成本与遗漏后果判断；能够推导的常用关系仍可能值得熟记。查用内容应先建立足以识别触发条件和使用边界的理解，不能把当前正确性、安全边界与必要判断所需的语义一并后置。

需要熟记的核心模型与关系，应在讲解建立该关系的位置用 `[!IMPORTANT]` 蓝色提示块突出，保留适用条件和判断用途。文末可以回顾与串联，不能代替首次讲解处的重点标识。标题直接概括对象、问题或关系，蓝框本身已表明掌握要求，不再添加“需要熟记”“重点记忆”等标签。

在复杂推导、命令表或文件对照等容易被误当成整体记忆任务的位置，应就近说明理解与查用要求；查用说明应保留核对时机与可靠入口。

## 重点取舍与提示块

应从整篇正文识别需要独立定位、反复调用，或容易忽略而影响判断的信息。具有独立取用价值的模型、方法、边界与工程取舍，应按内容职责使用提示块突出；当前例子的展开与状态推演通常留在普通正文，局部强调与精确映射可使用加粗或表格。可直接调整原段或提炼概括，以是否更便于理解与定位为依据。审阅同时检查应突出内容的遗漏与已有强调的适切性。

提示块按[内容职责](./markdown-callouts.md#内容与选型)选型。需要熟记的判断方法、易错边界和工程做法，仍按各自职责呈现；掌握要求与内容职责分别判断，不因信息重要就统一使用蓝框，也不为使用某个类型而增添内容。

- 核心结论应能解释当前示例并判断同类情形，保留对象范围与适用条件；术语名称或宽泛口号不足以构成核心关系。
- 判断线索应写出影响结果的条件、分支或判断顺序。
- 易错边界应写清具体错误预期或用法、触发条件、哪项假设不成立以及后果，不能只写“注意”或“容易出错”。
- 工程做法应说明约束、采用理由与影响选择的代价或局限，并区分语言规则、项目约定和有条件的建议。必要说明仍受知识依赖约束。

提示块可以包含关联的结论、解释与例子。按信息独立取用的需要决定合并或拆分，保留有助理解与回顾的概括，避免没有新增用途的重复强调。数量、长度和类型组合服从内容，不设固定句数、框数、段落比例或记忆条数。

## 准确性与证据

- 应区分语言保证、简化模型、实现选择与具体平台事实；工程建议另说明适用条件与取舍。模型和类比应标明当前解释的范围，不能据此给语言添加保证。
- 类型宽度、取值范围、ABI 与其他实现前提，应写在依赖它的示例附近。只在文末列出某个平台资料，不能代替当前推导所需的前提。
- 编译、诊断与运行结果用于核对示例；语言保证仍以对应标准规则为依据。不得用未定义行为的某次运行结果证明规律。
- 文末只保留与当前问题直接相关的标准条款或一手资料。引用应支持实际使用的结论，查用入口应对应需要核对的条件。

## 表达与排版

- 专业术语首次出现时使用中文与英文，后续沿用稳定、便于追踪的称谓，不要求读者持续在中英文之间换算。
- 正文应通过当前所需的解释与准确条件支撑结论，让目录承担导航；“暂时记住”等表述不能代替解释。有依据的掌握要求按前述分层呈现。
- 粗体只标记核心定义、关键区别、稳定模型和重要边界；标题不额外加粗，也不使用行内代码样式。提示块标题的具体写法按 [Markdown 提示块](./markdown-callouts.md#标题与写法)执行。
- 表格用于精确映射，图示用于关系或过程。简短正文已经清楚时，不增加视觉装饰。

## 审阅时的使用

审阅应覆盖以上全部适用要求，以及在当前范围内生效的关联规范。侧重点影响检查深度，不代替其他要求的核对；各节标题用于定位，不能只凭摘要或既有问题清单判断全文符合。

核对包括已经出现的内容，以及按要求本应出现却缺失的解释、条件、结果与提示。原则性要求应结合当前读者、问题和证据作判断，允许不同写法满足同一要求。

发现偏离时，应指出具体位置、未满足的要求及对理解或判断的影响。改进建议应与规范偏离区分；尚未读取的依据、未检查的范围或未完成的验证，应明确说明，不扩展为对全文的通过结论。
