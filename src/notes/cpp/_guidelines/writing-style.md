# C++ 笔记写作规范

## 定位

本规范只约束 `src/notes/cpp/` 下的 C++ 笔记正文、章节索引与附章，不约束个人站点的其他页面、其他学科笔记或仓库级工程文档。

C++ 笔记是兼顾顺序理解与长期查阅的个人知识体系：正文建立直觉完整、依赖闭合的知识主线，附章承载底层机制与更精细的标准规则。内容以 C++23 为准，不记录学习过程，也不追求像参考手册一样在概念首次出现时列全所有规则。

笔记通过稳定模型、明确的重点层级和就近的适用条件帮助理解与记忆。顺序阅读时，读者应能跟上当前解释，知道内容需要怎样掌握，并看出已有知识如何帮助理解新问题。笔记不承担练习、自测或学习进度跟踪职责；下文的构思问题与审阅清单供作者使用，不作为读者试题。

代码示例的命名、格式、接口倾向与标准库使用遵循 [C++ 代码规范](./coding-style.md)。

## 核心原则

> **窄入口，深模型；机制可以下钻，分类不横向蔓延。**

每篇只解决一个明确问题，并在当前知识边界内建立能够解释、推演和安全使用概念的最小准确模型。

**一个概念在当前层次建立完成，意味着读者能够准确解释并区分它，推演相似代码，识别当前范围内的失败边界，并在必要时得到真正成立的工程判断。**这也包括说明为何选择当前操作或接口，判断已有证据是否足以回答当前问题。正确直觉是必要起点，但只出现术语或只能复述类比，都不算完成语义建立。

- 新内容不得依赖尚未建立的语义才能被正确理解。
- 理解当前行为、边界与正确性所必需的使用语义必须先建立；只解释内部如何实现的机制可以进入附章。
- 高层抽象可以在其实现机制之前使用，但必须先给出足以判断当前行为的准确契约。
- 当前问题应当纵向抵达准确语义、可推演行为、失败边界和必要工程含义；停止深入的位置由真实的语义依赖决定，而不是由内容是否困难决定。
- 名称、符号或底层表示相近，不代表相关但不同的问题应当同时展开。章节按照要解决的问题组织，不按照术语表或符号表聚类。
- 较早建立的模型可以不完整，但不能依赖日后必须推翻的错误类比；后续内容只能扩充范围、补足机制或修正边界。

## 顺序阅读与理解成本

**正文的默认顺序阅读者已经读过前置内容，但缺少编程经验。**已引入一个概念，不代表读者已经能够熟练识别其不同写法、追踪多组对象关系或自行补齐省略的步骤。解释应从前文实际建立的能力出发；随着相同关系被反复使用，再逐步缩减支撑。

**阅读效率以读者掌握同一核心概念所需的总负担衡量。**除概念本身的必要难度，还应检查辨认符号、回忆前置、重建例子语境、追踪状态和筛选重点带来的额外成本。减少字数只有在不把这些任务转交给读者时才有价值；必要的展开可以使正文更长。

- 首次建立概念时，选择能够直接显现核心关系的情形，并说明当前范围。术语分类、通用规则与扩展边界按当前判断的实际需要引入；当前结论成立所需的限制必须就近保留，与当前判断无关的细节按对应问题组织。
- 新代码形式应说明当前用到的组成、名称角色、合法放置位置及执行结果。程序外壳和已经熟悉的部分尽量保持稳定；不为展示一种设施同时引入无关的库、业务背景或编程技巧。
- 复用前置关系时，就地恢复当前判断所需的最短联系，不让链接代替必要解释。跨段落继续推演时，明确仍在追踪哪个对象、值或调用；中间结果不易保留时，用名称、局部表格或图示把关系留在读者可见的位置。
- 能延续已有例子时，先推进它，再改变与新问题有关的条件。确需更换例子或表示时，交代保留了什么、改变了什么，以及为什么需要变化，避免让读者在每个小节重新认识一套背景。
- 让核心关系先形成可使用的判断，再组织背景与深入机制。首次掌握所需的语义与按需查用的说明应能辨认，避免读者尚未得到当前结论，就必须在多个未完成的问题之间往返。

这些要求用于选择组织方式，不规定每篇的术语数、代码行数或讲述步骤。已经熟悉的关系不必反复从头解释；必要的准确条件也不能为降低表面难度而删去。

## 内容分层

| 位置 | 职责 |
| --- | --- |
| 章节索引 | 说明本章解决的问题、关键关系和查阅入口，指出附章的阅读前提 |
| 主线 | 建立能够正确阅读、预测和使用当前概念的语义模型 |
| 附章 | 解释标准规则、对象模型、实现机制、平台差异和极端边界 |
| 综合篇 | 说明多个已建立概念共同解决的工程问题与设计取舍，不另起未经铺垫的知识主线 |

影响当前正确性、安全边界或工程判断的语义必须进入主线；只解释结论为何成立的内部机制可以进入附章。同一个结论可以在首次建立处集中解释，索引和后续正文根据查阅与推理需要作适当回顾。附章的位置以读者具备所需语义为依据；可以放在相关主线之后，也可以在附章内补齐必要的使用契约。

## 篇章构造与查阅

构思时可以围绕当前问题、主要结论、适用条件和容易误用的边界梳理内容。这些角度帮助取舍，不要求每篇逐项展开。准确性与必要的语义条件是质量要求；篇幅、段落、讲述顺序和强调方式则根据内容复杂度与阅读效果调整。

- 让读者容易找到当前问题与核心关系。可以先给结论再解释，也可以从例子、现象或矛盾逐步引出；采用哪种顺序，以是否有助于理解为准。
- 围绕清楚的关系组织段落，让抽象结论能落回当前对象、操作与结果。写出条件怎样影响结果以及推理所需的中间关系；连续的抽象术语或多层判断使论述难以跟随时，可以拆分或补充例子。
- 引入新表示时，说明它与已知对象或操作的对应关系；进入子问题前指出当前缺口，返回时恢复原目标与结果的用途。需要保存多个未完成关系时，可用局部表格或中间名称记录已知与未知；不要求每段重复目标或采用固定步骤。
- 让读者看出当前解释已经解决了什么，以及新增关系带来了什么判断能力。新例子应让已建立的关系用于判断新的情形；引入新规则或方法时，交代它解决的当前问题与适用条件。得到结论后，将结果落回该问题，说明已经能作出什么判断。
- 小节标题尽量帮助定位对象、问题或结论。适用条件与对应结论保持容易识别的联系，可以就近解释，也可以通过明确的回指或链接连接。
- 支持从单篇进入查阅：前置关系可以通过适量回顾、链接或前提说明帮助读者定位，根据当前论证需要选择，不必每篇补齐整条知识链。
- 当目录本身不足以呈现章节关系时，可以补充导读、关键区别或阅读前提。已有标题足以导航时，也可以保留简洁目录。

## 掌握要求

**作者应明确当前层次的掌握要求，让读者知道哪些关系需要熟记，哪些过程需要理解，哪些细节可以在使用时查阅。**重要性、强调形式与正文位置不能代替这项取舍。

| 掌握方式 | 选择依据 | 正文应交代的内容 |
| --- | --- | --- |
| 熟记并能直接调用 | 反复支撑阅读、判断或使用的概念关系、通用规则与操作模式；临场重建容易打断判断或遗漏关键条件 | 提炼可复用的关系及其适用条件，说明它用于什么判断，不把每个例子的具体结果都变成记忆对象 |
| 理解依据与必要时重建 | 用来解释结论或展示如何由已知关系得到当前结果的推理、计算与过程 | 写清中间关系，让读者能够说明依据或重建当前所需的判断；长篇推导和整段程序不要求逐句复述 |
| 使用时查阅并核对 | 依赖具体实现或任务而需逐次确认的数据与规格，以及当前只需识别触发条件的细则 | 说明何时需要查、核对哪些条件以及可靠入口；在依赖这些条件的操作之前完成核对 |

同一知识可以同时需要熟记关系、理解依据和查询精确细节。是否需要直接记起，要结合使用频率、重建成本与遗漏后果判断；能够推导的常用关系仍可能值得熟记。查用内容也要先建立足以辨认触发条件与使用边界的理解，当前正确性、安全边界和必要判断所需的语义仍须就地建立。

在复杂推导、细节表格或深入机制容易被误当成整体记忆任务的位置，用正文、索引说明或现有提示块交代掌握要求。表达方式按内容选择，不要求每篇设置固定栏目、记忆条数或读者练习。

## 重点的选择与呈现

根据内容承担的作用决定是否强调。提示块、加粗、表格或普通正文都可以承载重点；直接调整原段落，或在有助于回顾时提炼一段概括，都可以采用。判断依据是读者是否更容易理解和定位结论。

| 内容职责 | 选择思路 |
| --- | --- |
| 核心结论 | 能解释当前示例并用于判断相似代码的关系，保留必要的对象范围与适用条件；只有术语名称或宽泛口号不够 |
| 判断线索 | 给出影响结果的条件、分支或判断顺序；确有逐项对应关系时使用表格 |
| 易错边界 | 写清触发条件、哪一项假设不再成立以及具体后果，不只提醒“注意”或“容易出错” |
| 工程实践 | 说明实际用法及其理由，交代会影响选择的条件或取舍；区分语言规则、项目约定与有条件的建议 |

提示块的长度与结构由内容决定，可以包含结论、解释、例子或相互关联的判断。不设句数、数量或段落配额；是否拆分或移回正文，以是否更易理解和查阅为准。提炼时保留必要的对象范围与限制条件。工程建议沿用知识依赖要求，不为填充栏目提前引入尚未建立的设施。

提示块的语法、可选标题与使用建议见 [Markdown 重点提示](./markdown-callouts.md)。默认直接写正文；需要帮助定位内容时可以添加具体标题。

## 写作形式

- 专业术语首次出现时使用中文与英文，后续沿用便于追踪概念的稳定称谓，不因英文已经出现就要求读者持续在中英文之间换算。
- 示例只依赖已经建立的语义；标识符、格式和接口风格遵循 C++ 代码规范。
- 示例不得引入尚未建立且非当前结论所必需的语言设施或标准库工具；确实不可替代时，先建立足以理解示例的最小准确契约。
- 既有概念只保留完成衔接所需的最短回顾；正文直接陈述当前所需的知识关系，不用“第几篇已经介绍……”等章节进度代替解释。确需回指时，应同时写出当前论证依赖的结论。
- 用当前所需的解释与准确的使用条件支撑结论，让目录承担导航；“后面会讲”“暂时记住”等承诺不能代替当前解释。有依据的熟记要求按“掌握要求”交代其对象、用途与条件。
- 粗体只标记核心定义、关键区别、稳定模型和重要边界；标题不再额外加粗，也不使用行内代码样式。
- 表格用于精确映射，图示用于关系或过程；代码块使用完整程序，或注明嵌入语境的 C++ 片段。用于展示错误的代码应明确指出失败位置与原因。能够由简短正文说清的内容不增加视觉装饰。
- 示例数量以完成当前模型与判断能力为限。复用已有对象、操作或关系时，尽量维持一致的业务语境，让读者把注意力放在当前改变的条件与判断上。
- 对照示例应让关键区别实际显现，优先只改变影响当前结论的条件。展示错误直觉时，选择能暴露其后果的输入，并由正文直接解释结果；这属于论证，不是留给读者作答的练习。
- 类型宽度、取值范围和 ABI 等实现前提应写在依赖它的示例附近。编译、诊断与运行结果用于核对示例，语言保证仍以对应标准规则为依据；不使用未定义行为的某次运行结果证明规律。
- 文末只保留与当前问题直接相关的标准条款或一手资料。

## 审阅清单

完成或修改一篇 C++ 笔记后，可从以下角度审阅，结合文章类型与本次修改确定侧重点：

1. 这篇是否只解决一个明确问题，开头能否看出为什么需要讨论它？
2. 关键概念是否已经达到可解释、可区分、可推演的程度，主结论是否明确并保留必要条件？
3. 是否依赖尚未建立的语义、语言设施或标准库工具，或把已经介绍过的概念当成读者已经熟练掌握的操作；新代码形式是否有足够的使用契约？
4. 是否说明当前范围内的失败边界与常见错误直觉？
5. 是否区分语言保证、实现选择和平台事实？
6. 是否因名称、符号或实现相近而引入无关主题？
7. 示例中的类型、值类别、生命周期和求值过程是否一致，并符合 C++ 代码规范；对照输入是否确实显示了要解释的区别？
8. 主线、附章与综合篇是否职责清楚；附章的实际阅读位置或就地说明是否满足依赖；工程建议是否写清理由及影响选择的前提？
9. 跨篇回指是否写明当前所需的知识关系，而不是只汇报章节进度？
10. 顺读正文能否得到完整的因果解释，表示变化与子问题返回时能否跟上当前目标和对象关系；只扫标题、关键段落和表格时，能否找到主结论、适用条件及相关边界？
11. 当前需要熟记的关系是否明确；复杂推导、细节表格等是否容易被误当成整体记忆任务，必要时是否说明理解与查用要求，并保留当前使用所需的条件？
12. 新例子是否让已有关系解决了新的判断问题，新规则或方法是否补足了可辨认的缺口；所得结果及其足以回答的问题是否清楚？
13. 强调与回顾是否有助于理解和查阅，是否存在可以合并的重复内容或与当前问题无关的栏目？
14. 缺少编程经验的读者掌握当前核心关系时，是否还必须额外解析无关语法、重建业务背景、频繁跳转或同时保留多组未完成关系；能否通过调整例子、顺序或就地说明减少这些成本，并保留必要条件？
