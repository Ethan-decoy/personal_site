# 故障阶段与最小复现

“程序有问题”不足以指导调查。先确定最早失败的阶段，再选择证据和修复方向。

编译过程的职责边界见[从源文件到可执行程序](../compilation/source-to-executable.md)。多文件符号、声明与定义见[翻译单元、头文件、命名空间与 ODR](../compilation/translation-units-headers-namespaces-and-odr.md)。

若项目使用 CMake，配置、生成与 target 关系见[CMake Target、库与使用要求](../cmake/targets-libraries-and-usage-requirements.md)；编辑器或本机工具选择见[Visual Studio Code 与 CMake Tools 排障](../tooling/vscode-cmake-tools-troubleshooting.md)。

## 先判断现象属于哪一类

| 类别 | 典型现象 | 优先证据 |
| --- | --- | --- |
| 配置或生成错误 | CMake 尚未生成可用构建系统 | 第一条 CMake 错误、generator、缓存与 target 声明 |
| 编译错误 | 语法、类型或名称失败 | 首条 `error` 与源码位置 |
| 警告 | 构建可能继续，但有风险 | 警告指向的语义 |
| 链接错误 | 符号找不到或重复 | 符号、target 与签名 |
| 运行期故障 | 崩溃或工具报告 | 输入、调用栈与现场 |
| 逻辑错误 | 结果违反规格 | 最小用例的期望与实际值 |

这些类别是选择调查入口的标签，不是互斥的根因分类。未定义行为可能表现为崩溃或错误结果；启用 `-Werror` 时，警告也会使本次构建停止。

一个阶段失败后，后续阶段通常还没有可解释结果。编译没有成功时，先处理编译器证据；不要跳到运行输出上猜测。

## 从最早且最具体的证据开始

可以按以下顺序调查：

```text
配置或生成 error
-> 编译器 error
-> 尚未解释的 warning
-> 链接器错误
-> 异常退出或运行时工具报告
-> 与规格不符的结果
```

先修复最早的失败，再重新构建。一次随机修改多个位置会破坏因果线索，使人难以知道是哪项修改改变了结果。

## 警告需要解释

GCC 和 Clang 的学习项目常用：

```text
-Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion
```

具体警告集合和文字取决于编译器及版本。目标不是让文字消失，而是确认类型、范围和意图是否一致。强制转换只有在转换本身符合设计时才是修复。

项目还可以使用 `-Werror` 把警告升级为构建失败，但第三方代码或工具链升级可能带来新警告。是否启用以及在哪些 target 启用，应由项目策略决定。

## 构造最小复现

最小复现是仍能稳定产生同一问题的最小源码、输入、命令和环境说明。可以逐步移除：

- 与失败路径无关的输入和分支；
- 不影响现象的输出和函数；
- 无关的源文件与依赖；
- 与当前假设无关的构建选项。

每次只改变一项并重新验证。若现象消失，刚删除的部分可能是必要触发条件，也可能只是改变了未定义行为的表现，因此它是新证据，不是自动成立的结论。

## 退出状态与两个输出流

程序退出状态适合供脚本判断成功或失败：

```cpp
return all_passed ? 0 : 1;
```

正常结果通常写入 `std::cout`，诊断信息通常写入 `std::cerr`。文字供人阅读，退出状态供调用者稳定判断；两者不能互相替代。

日志看起来正常不代表退出状态为零，退出状态为零也不证明业务结果符合规格。调查时应同时保留实际命令、输出流和退出状态。

## 链接错误应该检查什么

遇到 unresolved、undefined、duplicate 或 multiple definition 等信息时，先记录完整符号名，再检查：

1. 提供定义的源文件是否属于当前 target；
2. 声明和定义的名称、命名空间及参数类型是否一致；
3. 同一普通外部定义是否被重复加入；
4. 当前命令是否链接了正确的库及配置。

这些问题背后的语言规则不在诊断页重复展开，请回到前述翻译单元与 ODR 笔记核对。

## 可复现的诊断记录

至少保留：

1. 最小触发输入或操作；
2. 源码版本与工具版本；
3. 实际构建或运行命令；
4. 第一条有解释力的错误信息；
5. 期望结果、实际结果与退出状态；
6. 修复后的回归检查；
7. 当前证据仍不能排除什么。
