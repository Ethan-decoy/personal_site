# 从规格到边界测试与回归保护

测试不是随便挑几个输入观察输出，而是把规格中的行为关系转换成可重复执行的检查。预期结果应从规格独立推导，不能照着当前实现反推。

## 先把规格拆成行为区域

假设输入类型是 `int`，规格为：

```text
reading < -4          -> 7
-4 <= reading <= 18  -> 8
reading > 18          -> 9
```

它包含三个行为区域和两个阈值。因为参数类型是 `int`，区域受该类型的最小值和最大值约束：

```text
[INT_MIN, -5]    [-4, 18]    [19, INT_MAX]
```

也可以把两端写成 `(-∞, -4)` 与 `(18, +∞)` 作为数学简写，但真实输入域始终是这些集合与 `int` 可表示范围的交集。

每个区域至少选择一个代表值。为了发现 `<` 与 `<=` 混淆，还要直接检查阈值以及可表示的相邻整数：

| 分界点 | 前一个整数 | 分界点本身 | 后一个整数 |
| --- | ---: | ---: | ---: |
| `-4` | `-5` | `-4` | `-3` |
| `18` | `17` | `18` | `19` |

```cpp
check_equal(7, signal_code(-5));
check_equal(8, signal_code(-4));
check_equal(8, signal_code(-3));
check_equal(8, signal_code(17));
check_equal(8, signal_code(18));
check_equal(9, signal_code(19));
```

“前一个”和“后一个”来自 `int` 的离散取值。若阈值是 `std::numeric_limits<int>::min()` 或 `max()`，对应一侧没有可表示的相邻 `int`，不能直接计算 `threshold - 1` 或 `threshold + 1`。

浮点数也不能机械套用“减一、加一”。应根据该规格的精度和允许误差选择输入；如果必须检查相邻可表示浮点数，再使用专门的浮点工具。

## 分支覆盖不等于边界覆盖

假设实现把 `reading <= 18` 错写成 `reading < 18`。测试 `-5`、`0`、`19` 仍会分别执行三个分支，却不会发现输入 `18` 被错误分类。

因此要分别列出：

1. 每个行为区域的代表值；
2. 每个关键阈值及其可表示的邻居；
3. 若规格声明了合法范围，检查范围之外的输入；
4. 若接口存在合法失败或无结果状态，检查每一种状态。

分支覆盖回答“哪些控制流分支执行过”，边界测试回答“规格在分界处是否实现正确”。两者提供不同证据。

## `expected` 与 `actual`

一个最小检查函数可以写成：

```cpp
bool check_equal(int expected, int actual)
{
    if (expected == actual)
    {
        return true;
    }

    std::cerr << "expected " << expected
              << ", actual " << actual << '\n';
    return false;
}
```

`expected` 来自规格，`actual` 来自被测函数的真实执行结果。C++ 不会判断两个同类型实参是否放反，因此调用点应始终保持相同顺序。

## 让每个检查真正执行

如果希望一次运行看到全部失败，不要用短路表达式串联有副作用的检查：

```cpp
bool all_passed{true};

if (!check_equal(7, signal_code(-5)))
{
    all_passed = false;
}

if (!check_equal(8, signal_code(-4)))
{
    all_passed = false;
}

return all_passed ? 0 : 1;
```

这样两个检查都会执行，最终退出状态仍能汇总结果。`0` 表示整体成功，非 `0` 表示至少有一项失败。

## 先固定失败，再修复

发现缺陷时，先写出能够稳定失败的最小检查，再修改实现。修复后保留该检查，它就成为回归保护：

```text
复现缺陷 -> 固定预期 -> 修复实现 -> 保留检查
```

回归检查只能证明这个具体行为在本次构建和输入中通过，不能证明整个程序没有其他缺陷。

## 准确描述覆盖范围

`int` 的取值集合有限，但通常仍不会逐个执行。测试报告应写清实际覆盖的区域、阈值和样例，不要声称“所有 `int` 输入都已测试”。

一份诚实的说明可以是：

```text
执行了三个行为区域的代表值，以及 -4 和 18 的相邻整数。
没有穷举 int 的全部可表示值。
```

## 检查清单

1. 预期结果是否直接来自规格？
2. 每个行为区域是否有代表值？
3. 每个关键阈值是否检查了可表示的相邻值？
4. `expected` 与 `actual` 的位置是否一致？
5. 一个失败会不会短路跳过后续检查？
6. 退出状态能否供脚本可靠判断？
7. 覆盖声明是否只声称实际执行过的内容？
